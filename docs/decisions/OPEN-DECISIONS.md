### 流程纪律（2026-10-27 晚沉淀 · 负责人要求立为规矩）

| 纪律 | 起因（本轮**真实踩到**，不是预防性假设） | 规矩 |
|---|---|---|
| **提交一律带 pathspec，或提交前逐行确认暂存区归属** | `git commit` 未带 pathspec ⇒ 把运维**已暂存**的 5 个文件一起提了（`0dcf28d` 实际含 7 个文件）。多人共用同一棵工作树时，「暂存区是谁的东西」**不是默认可知的** | 用 `git commit -- <paths>` 显式限定；或提交前 `git status` 逐行确认。⛔ **已 push 的提交不拆**：本仓 main 只 ff，拆 = force push，会让别人本地 diverge、可能吞掉别人刚拉到的东西；而它换来的只是「`git blame` 作者名更准」—— **记账问题，不值得动远端历史**。归属问题记在 commit message 正文里，比强行改历史诚实 |
| **带反引号 / `$(...)` 的 commit message 必须走文件** | `git commit -m "..."` 里有 `` `文件:行` ``，bash 把反引号当**命令替换**执行 ⇒ 所有 `文件:行` 引用**变成空串**（提交信息当场失真） | 用 `git commit -F <file>`（或 heredoc）。⚠️ 补救边界：**amend 只可用于未推送**的本地提交；已 push 的只能靠 force push，本仓不许 |
| **「报错但已生效」必须回读确认，别只看退出码** | `git commit` 打印 `fatal: cannot lock ref 'HEAD'`（并发提交抢锁），但**提交其实落了** | 这类情况一律 `git log -1` / `git show --stat HEAD` 回读确认真实状态，再决定下一步 |
| **容器时间戳类证据要先问「它记的是事件还是状态」** | `docker inspect` 的 `StartedAt` 被当成「容器首次启动时间」去比启动顺序 ⇒ 推出一条错误的「api 起在 redis 前面」结论，并据此主张了两轮。它记的是「**当前这次启动**」这个**事件**，不是「已运行多久」这个**状态** | 取证先确认时间戳语义。**能用代码语义推运行期状态时优先用它**：本例 `auth:login` 限流是 fail-closed ⇒ 拿到 201 就证明 KV 的 `incr` 成功 ⇒ 那一刻 Redis 健康且已就绪 —— **不需要任何关于时间戳的假设** |
| **日期/时间/中文值取证一律取整数、epoch 或 HEX，不采信渲染后的明文串** | 生产 MySQL 的 datetime 串在我这侧渲染成了**不可能的日期**（`2026-10-27` 这种形态），差点据此报「服务器时钟坏了」；但 `YEAR()/MONTH()/DAY()` 三个整数、`NOW()+0`（`20261027211444`）、本机 `date +%s` 三者一致 ⇒ **库里时间是对的，是观察通道的渲染偏差**。测试侧同日独立撞到同一现象，改用 `HEX(CAST(updated_at AS CHAR))` 解码才拿到真值（见「曾误判日期写成 7 月 32 日」那一行） | 时间取 `YEAR/MONTH/DAY` 分字段或 `+0` 数值形态或 epoch；中文值取 `HEX()` 比字节。⛔ 不拿回显里的明文日期串下结论 —— **它区分不出「时钟坏了」和「渲染偏了」**（与上一行同类：证据必须能区分它要判的两行） |
| **判据必须能区分它要判的两行** | 用「日志里出现了 `Command timed out`」去断言「缺陷仍在」，而该文本在「Redis 真不可用」时**本来就该出现** ⇒ 这条证据区分不了「缺陷残留」与「正确拒绝」 | 判据按**原因**定，不按**现象**定（本例正确判据：**只有 Redis 健康且已就绪时仍超时，才算残留**）。另注：顺着「缺陷仍在」往下走的唯一解法是放宽 `commandTimeout`，而那会把 fail-closed 从「拒绝」退化成「挂住」（请求不返回、连接占满、连错误日志都看不到） |
