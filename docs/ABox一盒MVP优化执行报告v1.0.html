关键技术风险与对策

#风险对策
1cutoff-task / auto-confirm 定时跑批漏跑、重复跑幂等设计（状态机条件 UPDATE 影响行数为 0 即跳过）+ 每分钟补偿扫描（找回滞留在 paid>24h / delivered>14:00 的订单）+ 操作日志留痕
2多集散中心并行数据一致性每个「日期 × 楼群」分配唯一（uk 约束），份数快照在截单时冻结到 ab_supplier_dish_daily.plan_quantity；集散中心只读自己的行，无跨中心写冲突
3反向分账（已分账后退款）方案 B 人工月结下：T+1 报表标记「待回退」，从下次应分账金额中抵扣（原型 P32 已演示该口径）；方案 A 上线后走微信分账 return
4RabbitMQ 必要性结论：MVP 不引入。日单量 ≤500，用 Redis 7（BullMQ 延迟队列）承载截单/确认/结算 3 个定时场景足够，省运维与 3–4 人天；消息量上来后二期再评估
