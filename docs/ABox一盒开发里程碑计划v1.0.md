### 目标
打通"登录 → 下单 → 支付 → 看订单"四条骨架，让用户端**主链路在真机上无断点**。

| 1.3 | 种子数据导入（12 楼 / 5 楼群 / 4 供应商 / 4 集散中心 / 菜品库 / ¥25.80 / 4 级佣金） | `database/seeds` | 1.2 |
| 1.4 | 微信登录（`code2session`）+ JWT 下发 + `auth.guard` | `modules/auth` | 1.2 |

### 交付物
- 可运行后端（`pnpm dev:api`）+ Swagger 已含 U1–U11
- 微信开发者工具可打开的小程序，用户端主链路可点击走通
- 单测：状态机、下单幂等、取消窗口

### 验收标准
1. 微信授权后直接进入首页，**不索要手机号 / 地址**（L9）
2. 下单 → 支付成功 → 支付结果页 → 订单详情，状态依次为 `pending_pay → paid`，与《状态机 v1.0》§1.2 三视角文案一致
3. 截单前取消成功、金额原路退回；**截单后调取消接口返回 40004**
4. 同一幂等键重复下单只产生一单
5. 倒计时显示距当日 24:00 的真实剩余时间

### 风险
微信支付商户号实际可用性（**已于准备期核对，若额度/权限异常将阻塞 1.8**）

## 二、M2 · 团长端全链路（W5）

### 目标
跑通"团长看到本楼单量 → 接收取餐提醒 → 一键分发 → 佣金入账 → 提现"，并落地**代退申请**入口。

### 任务分解

| # | 任务 | 落点 | 依赖 |
| --- | --- | --- | --- |
| 2.1 | 团长叠加身份（`isLeader` 服务端判定 + 本地持久化） | `modules/team-leader` | M1 |
| 2.2 | 团长申请：提交即生效（C3） | `modules/team-leader` | 2.1 |
| 2.3 | 工作台 / 本楼概况 / 订单明细（P11–P13） | `miniprogram/pages/leader` | 2.1 |
| 2.4 | **代退申请**（C6 第一段：只登记，不退款不回退） | `modules/finance/refund` | 2.3 |
| 2.5 | 取餐确认 + 一键分发（按**实发份数**计入佣金） | `modules/order` | 2.3 |
| 2.6 | 佣金中心 / 余额流水 / 提现申请（P16–P18） | `modules/finance` | 2.5 |
| 2.7 | 分享中心 + 小程序码生成（P19） | `modules/team-leader/share` | 2.1 |
| 2.8 | 团长资料 + 退出团长身份（P20） | `miniprogram/pages/leader` | 2.1 |
| 2.9 | 推荐裂变与晋级审计（"介绍 N 名转正"数据落表） | `modules/team-leader/invite` | 2.2 |

### 交付物
- 团长端 P11–P20 全部可点击
- `ab_leader_invite` 表落库，晋级审计可查
- 单测：代退申请**不改订单金额、不触发退款**；佣金按实发份数计算

### 验收标准
1. 用户在"我的"可申请团长，**勾选协议后立即生效**，tabBar 出现团长入口（无审核流程）
2. 团长对本楼订单发起代退申请后：`ab_refund.status='applying'`，订单进入 `refund_applying`，**资金未动**
3. 一键分发后佣金按 `实发份数 × 等级费率` 计算，与余额流水一致
4. 提现申请可提交并进入待审批

### 风险
佣金基数口径（实发 vs 下单）—— 已定稿"按实发"，实现若用错会导致全站佣金偏差

### 目标
把"夜里自动跑批、次日自动入账、关键节点自动触达"打通 —— 这是**不依赖人操作**的兜底能力。

| 4.2 | `cutoff.task`（T-1 24:00 截单：取消未支付 + 锁定 + 推备料量） | `tasks` | 4.1 |
| 4.3 | `delivery-generate.task`（T 日 00:30 生成配送单） | `tasks` | 4.2 |
| 4.4 | `auto-confirm.task`（T 日 14:00 自动确认 + 写佣金） | `tasks` | M2 |
| 4.5 | `commission-settle.task`（T+1 02:00 佣金入账） | `tasks` | 4.4 |
| 4.6 | `supplier-share.task`（T+1 02:00 生成应付，**不拨款**） | `tasks` | M3 |
| 4.7 | `reconciliation.task`（每日 04:00 对账） | `tasks` | M1 |
| 4.8 | **`leader-expire.task`（每日 03:00 见习团长 30 天未促单失效，C2）** | `tasks` | M2 |
| 4.9 | Redis + BullMQ 三消费者（支付后续 / 退款申请 / 结算后续） | `queues` | 4.2 |
| 4.10 | 微信订阅消息（支付成功 / 出餐提醒 / 取餐通知 / **退款结果必推**） | `modules/message` | 4.4 |
| 4.11 | 幂等与重试：所有任务以 `meal_date` 为幂等键，失败可重放 | `tasks` | 4.1–4.8 |
| 4.12 | 财务"付款登记"（人工对公：登记回单号 + 发票号，改应付状态） | `views/finance` | 4.6 |

### 交付物
- 8 个定时任务上线，可控触发（含手动补跑接口）
- 消息模板在后台可配置
- 单测：任务幂等（重复触发只生效一次）、反向结算金额、佣金入账金额

### 验收标准
1. 模拟 T-1 24:00 触发截单：未支付订单全部 `cancelled`，已支付转 `cut_off`，4 家供应商收到备料量
2. T 日 14:00 未确认的订单自动 `completed` 且佣金入账（**不依赖团长操作**）
3. 每个任务重复触发 **不产生重复数据**
4. 退款结果**必推**订阅消息（用户可感知）
5. 供应商应付单生成后**不自动打款**，财务在后台登记回单号后状态转 `success`

## 五、M5 · 三方联调 + 灰度上线（W9）

### 目标
一个办公楼（建议**国贸三期 A 座**，示例团长李明所在楼）真实闭环跑通。

### 任务分解

| # | 任务 | 说明 |
| --- | --- | --- |
| 5.1 | 端到端联调（用户端 / 团长端 / 供应商端 / 后台四条链路交叉验证） | 按《状态机 v1.0》§七 状态↔接口↔表 对照逐项过 |
| 5.2 | 压测 / 稳定性（当日单量峰值、跑批窗口不重叠） | 目标：单楼 500 单/日无超时 |
| 5.3 | 安全自检（越权、幂等、重放、密钥泄露、日志脱敏） | 对照《协作规范 v1.0》§五 |
| 5.4 | 生产环境部署（Docker + K8s）+ 域名 / HTTPS / 白名单核对 | 见《账号资源与密钥清单 v1.0》 |
| 5.5 | 灰度：单楼开团 → 观察 3 天 | 每日核对：订单数、结算等式闭合、佣金、退款链路 |
| 5.6 | 应急预案演练（回滚、截单窗口故障、支付回调异常） | 禁发窗口：T-1 23:30–24:30、T 日 10:00–12:30 |
| 5.7 | 试运营交付与培训（团长 1 页操作卡 + 供应商 1 页出餐卡） | — |

### 验收标准
1. 一个办公楼完整跑通 **3 个自然日**（含一次完整跑批与一次退款）
2. 单份结算账实相符（等式闭合）：**协商供价（示例 ¥14.00）+ 场地费（默认 ¥0）+ 打包人工 + 配送费 + 佣金（按等级）+ 毛利（结果值）= ¥25.80**
3. 无 P0 缺陷；P1 缺陷 ≤ 3 且均有临时规避方案
4. 回滚演练成功（10 分钟内可回退上一个版本）


| 缓冲位 | 预留 | 用途 |

| W8 末 | 0.5 天 | 跑批联调缓冲 |
