## 四、唯一缺陷：取消理由的后台闭环断裂（**已修复**）

> 状态：**2026-10-04 当日修复并回归** · 提交 `9b871be`（已推 `origin/main`）· 复跑 `all 24/24` / `verify 4/4` / 第三层 `82/82` 全绿。

### 现象

取消理由这个功能，是跟着同事的建议做的：「取消订单时给取消理由，**用于数据分析**」。
现在的状况是：

- ✅ 用户在小程序端选理由 → 落到 `ab_order.cancel_reason / cancel_note / cancel_source`；
- ✅ 系统截单（source=system）与团长代退（source=leader，驳回时三列配对清空）也都在落；
- ❌ **运营在后台订单列表看不到、详情页看不到、导出 CSV 里也没有这三列**。

也就是说：数据躺在库里，但**没有任何一个界面能把它取出来做分析**，除非人工连数据库写 SQL。
功能只做了一半 —— 采集端完成，消费端缺失。

### 根因（代码层交叉验证，不是探针写错）

`apps/api-server/src/modules/order/order-admin.service.ts`：

1. `decorate()`（第 609–652 行）—— 列表与详情**共用**的组装函数，返回对象里没有
   `cancelReason / cancelNote / cancelSource` 三个键（这就是 E2/E4 报红的位置，同一处根因导致两处红）；
2. `exportOrders()`（第 449–466 行）—— 16 列表头里同样没有「取消」相关列（E6）。

配套的中文映射 **`CANCEL_SOURCE_LABEL` 与 `CANCEL_REASON_LABEL` 已经备好在 `cancel-reason.dto.ts`**，等于零件齐全、只是没接上。

### 已落地的修复

| 步骤 | 动作 | 文件 | 结果 |
|---|---|---|---|
| 1 | `decorate()` 补 `cancelSource` / `cancelSourceText` / `cancelReason` / `cancelReasonText` / `cancelNote`（**缺失一律 `null`，刻意不填空串**） | `apps/api-server/src/modules/order/order-admin.service.ts` | ✅ +25 行 |
| 2 | 导出表头与行值补「取消来源 / 取消理由 / 取消说明」三列（**16 列 → 19 列**，插在「状态」之后、「备注」之前） | 同上 | ✅ +13 行 |
| 3 | 同步**真源**《ABox一盒接口规范 v1.0》D8/D12 段（含「为什么 null 不填空串」的统计口径说明） | **工作区根**（非 `docs/` 产物） | ✅ +2 行 |
| 4 | 回归链：`sync-docs` → `doc:tables` → `gate.mjs all` → `gate.mjs verify` → 第三层探针 | — | ✅ 全绿 |

**为什么缺失时给 `null` 不给空串**：空串与「未采集」在 Excel 里看不出区别，会把
`cancelReason` 为 null 的统计语义（`= 用户跳过了，不是没有`）吃掉 —— 而这条语义
正是 `CancelReason` 契约里反复强调的「先按 `cancelSource` 分层，再算未填占比」的前提。

## 五、顺带沉淀的业务口径（以后以此为准）

| 事实 | 判据来源 |
|---|---|
| 单笔份数上限 **1–20**（`ab_config.order.max_quantity`），超出 code=30002 | F1 |
| **日累计份数仍无上限**：一天可下多单，每单最大 20 份 ⇒ 理论上不限量 | F1 + F4（待你定要不要加日上限） |
| 取消说明 **100 字是硬边界**，列 `VARCHAR(128)` 余留 28 字 | D4/D5 |
| 取消理由**可跳过**；跳过时 `reason=NULL` 但 `source` 照记（区分「不愿说」与「系统清掉」） | deep-cancel C7/C8 |
| 代退路径：**驳回必须把三列一起清空**，否则会出现「订单回到 paid 却带着取消标记」的脏数据 | deep-cancel C22 |
| 资质墙是**免登录**接口，出参为显式白名单，当前无联系人 / 银行 / 商户号泄漏 | G4 |
| 资质墙分组与 S1 出餐前置**同源**（`canServe`），证照过期即刻同步 | G1/G5 |

## 六、探针自身的两个坑（防复发）

1. **F 组必须按「进场基线 + 增量」断言**，不能写死数字。
   实测写死 `count=2` 会得到 4 —— 因为探针自己的 D 组有意留了两张未取消的 pending 单（D4b 被拦下的、D6b 他人取消不了的）。
   这是**夹具没隔离导致的假红**，不是产品算错。
2. **G 组要自造样本**：种子里 4 家在供 / 6 家暂未供应，`inactive` 其实非空（第一轮那条 A14 不算「恒绿」），
   但用「把某家有效期改成昨天」能额外验证**分组是即时计算的**，这条能抓出「列表判据与出餐判据漂移」——
   单纯断言静态分组抓不到。
