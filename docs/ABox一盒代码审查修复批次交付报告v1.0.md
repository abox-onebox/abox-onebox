## 一、改了哪些（按风险从高到低）

### 1. 资金链并发三连 + 静默资损（审查 §三.2 / .3 / .4 → 账本 #80 / #81 / #82）

这是本批**唯一涉及真金白银**的部分，四处改动合起来是一件事：**把「先读再写」换成「让数据库判归属」**。

| 位置 | 旧写法（为什么危险） | 新写法 |
| --- | --- | --- |
| `refund.service.ts` `settleRefundDb` 入口 | 先冲销账务、最后**无条件** `UPDATE ab_order SET status='refunded' WHERE id = ?` | 第一步就 **`UPDATE … WHERE id = ? AND status IN (…)`**，`affected = 0` → `40008` 并**回滚整个事务** |
| `refund.service.ts` `approveByAdmin` 审批落库 | `findOne` 判状态 → `m.save(refund)`（**无条件全列覆盖**） | 合成**一条带条件的 UPDATE**（`WHERE id = ? AND status = 'applying'`），`affected` 判归属 |
| `reversal.service.ts` 余额退回 / 佣金冲销扣款 | `.where('id = :id')`（`version` 只出现在 `SET` 里） | `.where('id = :id AND version = :v')` + `affected = 0` → **`40018`** |
| `commission.service.ts` 佣金入账 | 同上（**唯一把钱写进余额的地方**） | 同上（`40018`，**整批回滚** —— 结算可重入，重跑即可补齐） |
| `reversal.service.ts` 无余额账户分支 | `logger.warn + return 0`（**静默跳过**，而出参仍报「已退回」） | **fail-closed** 抛 **`40019`** |

**为什么「一处原子占位」比「逐段加守卫」好**：前者一处同时守住**余额 / 佣金 / 通道三段**；后者的失败模式恰恰就是本条缺陷本身 —— 有人修了佣金忘了余额（账本 #77 记录了这个「修好一半反而更隐蔽」的过程）。占位**与收口合并为一次写**，因此不引入新的中间态、状态机无需改，且事务失败时不会留下「占住了但没退」的僵尸单。

**两处刻意的「不统一」**（写进代码注释，否则下一个人会来「统一」掉）：
- 佣金冲销扣款**找不到团长账户时保留「仅记账、不扣款」**（不 fail-closed）—— 那是数据异常，**动钱**才是更大的错。
- 佣金入账拿到 `40018` 时**整批回滚**而不是在事务内重试 —— MySQL REPEATABLE READ 下同事务内重读仍可能拿到旧快照。

**前端 + 注解：幂等键补齐（#80 的「叠加因子」）**
- `admin-web/src/api/request.ts`：请求层**兜底注入 `Idempotency-Key`**（方法 + 地址 + params + body + **60 秒时间窗**指纹 · FNV-1a · **显式传键优先**）。
- 6 类写端点补 `@Idempotent({ required: false })`：提现 4 端点、佣金补跑、手动改单、强制退款、退款审批、退款驳回。
- ⚠️ `required: false` 是**刻意**的：这些端点**已有数据库级闸门**，幂等键是**第二层**（挡网络重试/双击，让端上拿到**首次结果**）；强制请求头只会让 curl / e2e / 集成方一律撞 `10001`。

### 2. 安全默认值 + 门禁豁免盲区（审查 §三.6 → #83）

**先纠正审查报告的一处因果**（重要）：报告写「`security-scan` 的 `PLACEHOLDER` 豁免把 `'change_me_before_go_live'` 当示例放过了」。**实测不成立** —— 直跑基线 **全绿**，根因是**压根没有规则命中这类默认值**。**没有命中，就谈不上豁免。**「因果写反」会让修法完全跑偏：按原判断去改豁免正则，改完门禁照样绿、缺陷照样在。

故修法是三步：
1. **先加规则**：`PATTERNS` 新增「敏感配置的危险默认值」（`?? / || / str( / num(` 之后 60 字符内的危险字面量，FAIL 级）。⚠️ 带 `history: false` —— **不进 git 历史扫描**，否则「已修好的旧提交」会让门禁永远红。
2. **豁免按位置收窄**：`PLACEHOLDER` 只在**注释内**生效；另加**显式标记** `security-scan:allow`（可带理由、可审计）。
3. **生产 fail-fast**：`main.ts` 启动期缺 `JWT_SECRET` → `exit(1)`，禁止任何默认值。

⚠️ **本轮踩到两次的坑（已成纪律）**：`security-scan:allow` 标记**必须与目标行紧邻**（同行或紧接上一行）—— prettier 折行后写在注释块**首行**会**静默失效**。凡「靠标记豁免」的机制，都必须有一条「断言豁免真的生效了」的自证。

### 3. 其余加固项（审查 §三.5 / .7 / .11 / .12）

| 项 | 旧 | 新 |
| --- | --- | --- |
| `seed` 清库（**27 张表**） | 只认 `NODE_ENV` 一道 | **双守卫**：非生产 **且** `ABOX_SEED_CONFIRM=1`（`gate.mjs seed` 已注入） |
| CORS | `cors: true`（反射任意 Origin） | `CORS_ORIGINS` **白名单**（未配时：非生产放行 / **生产拒绝**） |
| 安全响应头 | 无 | `nosniff` / `X-Frame-Options` / `Referrer-Policy` + 去掉 `X-Powered-By`（**刻意不装 helmet**：本机无 pnpm，为三个头引依赖链不划算 —— 理由写进注释） |

## 二、新增的那道门禁（本批技术含量最高的一件）

**`apps/api-server/src/modules/order/order-state-audit.ts`** · 门禁名 **`state:audit`**

它回答一个此前**没有任何门禁问过**的问题：**状态机声明的迁移目标，生产代码真的写过吗？**

- **判据（状态级）**：① 声明为迁移目标的状态必须有写入点；② 写入的状态必须在状态机内登记；③ **豁免自收紧** —— 一旦某项被实现，门禁立刻要求删除豁免。
- **豁免是可见的**：未实装的状态写在 `UNIMPLEMENTED_TARGETS` 里（每条带理由 + 账本引用），且**每轮都打印在门禁输出里**。「能力没做」从此是 CI 里**可见的一行**，而不是一个看不见的洞。
- **三重自证** + **反证测试**：人为删目标 / 塞幽灵状态 / 加过期豁免，三种都必须报出，否则门禁自身失败。
- ⚠️ **边界（如实标注）**：只做**状态级**、不做**迁移边级**（守卫形态多变，静态配对必然误报）；无法静态判定的写入点**显式列为待人工确认**，绝不静默跳过。

⭐ **反证测试当场抓出我自己的一个洞**（这条比门禁本身更值钱）：首版扫描器只匹配两种合法写法，于是 `status: 'ghost_state'`（**拼错的字面量**）落不进任何分支、被归成「动态值」**静默放过**（塞进去后门禁仍 exit 0）。修法：**捕获 `status:` 右侧任意原文再分类**。「静态可判定的一律判定，只有真动态才留给人」。
→ 结论：**任何新写的检查器，在被反证过一次之前，它的「绿」不构成任何证据。**

⭐ **该门禁首跑即报出第二处漂移**（此前无人登记）：`ORDER_TRANSITIONS[refund_applying]` 仍声明 `→ refunding`，而 **M4-3 起「订单」不再进入该态**（通道进度改由 `ab_refund.status` 表达）—— 属**声明表 ↔ 实现的口径漂移**，已登记待裁决。

## 三、验到什么程度（**这一点比「改完了」更重要**）

### 机械可验的部分（已验，全绿）

| 验证 | 手段 | 结果 |
| --- | --- | --- |
| 幂等键真的挂在路由上 | e2e §33b(A)：同键二次提交 | **HTTP 200 + `code 10006`**，且 `data` **与首次逐字段相同**（是**幂等回放**，不是简单拒绝）；换键立刻放行 |
| 乐观锁真的执行了 | e2e §33b(B)：退款成功后 `ab_balance.version` | **恰好 +1** |
| 出参反映真实退回额 | e2e §33b(B)：`balanceRefundedFen` | `= 5160`（分），与账务一致 |
| 无账户 fail-closed | e2e §33b(C)：审批退款 | **`40019`**，且订单仍在 `refund_applying`、退款单仍在 `applying`、**流水一条未写**（整体回滚） |
| 同一单不被退两次 | e2e §33（既有，继续绿） | 两条 `applying` 单 → **恰好一条成功**，余额流水恰好 1 条 |
| 门禁 / 构建 / 单测 | `gate.mjs all` | **20 道全绿** |

### ⚠️ **仍然验不了的部分（必读，别把上面的绿读成「并发已验」）**

**`better-sqlite3` 是单连接同步驱动 → 两个事务被串行化** ⇒ **本地任何「绿」都不构成并发安全的证据。**

| 项 | 为什么本地测不了 | 怎么验 |
| --- | --- | --- |
| #80 真并发双付 | 单连接串行化；且 `genRefundNo()` 每次生成新 `out_refund_no`，**两个不同键对微信就是两笔单** | **真机 MySQL** + 两个并发请求打同一单 approve |
| #81 余额丢更新 | 同上 | **真机 MySQL** 并发「退款退回」∥「T+1 02:00 佣金入账」 |
| #83 启动 fail-fast | 需生产形态配置 | 不设 `JWT_SECRET` 启动，应**失败** |
| 新增 CORS 白名单 | 需真实域名 | 生产配 `CORS_ORIGINS` 后验后台与端上都能通 |

⭐ 特别提醒一条**容易误读的绿**：`version` 恰好 +1 这条断言，**证不了「并发下不丢更新」** —— 把 `WHERE` 里的 version 条件整段删掉，它**仍然会过**。故它与「真机并发验证」**必须成对存在**，单看任何一半都会给出**错误的安全感**。

## 四、**没有改**的（如实登记，不是遗漏）

### 1. ⛔ #79 履约链 T7–T9（P0）—— 需产品范围裁决，本批**未改实现**

`ab_order` 的 `cooked` / `delivering` / `delivered` **仍全仓零写入点** → 订单支付后停在 `cut_off`；团长「确认取餐」永远返回零值（**不报错**）；**佣金永不产生**；自动确认跑批每天把当天全部订单报成「履约异常」。

本批做的两件事：
1. **测试清单已标注依赖**（见 §五）—— 否则测试者必然全报 P0 并浪费一整轮。
2. **结构性根因已建门禁**（§二）—— 让这个洞在 CI 里可见。

**待裁决的三个选项**（原报告 §三.1）：① 补实现（推荐）；② 本期不上履约，把 L9/T11 准入门槛放宽到 `cut_off`；③ 维持现状 + 在文档与测试清单里如实登记。**给出选择即可，实施我这边是一天内的事。**

### 2. 其他如实登记项（未改，附原因）

| 项 | 为什么没改 |
| --- | --- |
