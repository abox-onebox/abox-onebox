## 一、产品一句话描述（可直接抄进「小程序简介」）

> ABox 一盒是面向写字楼的**当日现做盒饭**预订小程序。用户在前一天 24:00 前预订次日午餐，
> 由所在楼宇的「团长」统一取餐分发；每盒固定一饭四菜，同一价格、统一出品。

⚠️ **抄之前先确认两件事**（都会改变简介措辞，见 §十一）：

1. **产品形态归类**（自营出餐 / 平台撮合）——影响服务类目，属**待裁决**，未定前不要写死；
2. **对外是否使用「中央厨房」标签**——属**待裁决**，写上去就要拿得出资质。

⚠️ **两条别踩**：

- **同一身份同一业务日只能下一单**（这是业务规则）。多人同时用 `dev:1001` 测试，

- `1002 / 1003 / 1004` 同时是「已跟随李明的成员」**且自身也是团长**，
  这是刻意造的边界样本（楼栋转交 + 费率快照），**两个身份都对**，不是数据错。

## 四、无需真实支付的测试路径（§6.2 第 7 条）

审核员**不需要真实支付**就能看到支付后的全部页面：

| 开关 | 默认 | 作用 | 真源 |
| --- | --- | --- | --- |
| `PROVIDER_MODE` | 生产 `real` / 其他 `mock` | `mock` 时登录用 `dev:<标识>`、支付走 Mock | `app.config.ts:33` |
| `MOCK_PAY_AUTO_SUCCESS` | `true` | 发起支付后自动回调「支付成功」 | `app.config.ts:134` |
| `MOCK_PAY_CALLBACK_DELAY_MS` | `800` | 自动回调延迟（毫秒） | `app.config.ts:135` |

**审核员的操作**：下单 → 点「确认支付」→ 等约 1 秒 → 自动跳「支付结果」成功页 →
后续「订单详情 / 我的订单 / 团长端」全部可见。

> ⚠️ `PROVIDER_MODE` 的默认值 2026-09-25 已改：生产缺省 **`real`**（原来是 `mock`），
> 且生产缺配会**启动中止**并打印明确 ERROR（`main.ts` 必配项检查）。
> 原因：原默认值 `mock` 意味着**漏配也能启动**，结果是任意 code 免密登录任意身份、
> 支付自动置为已支付——这是生产不能有的兜底。
