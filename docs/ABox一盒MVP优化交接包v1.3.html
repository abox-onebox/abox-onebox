一、30 秒读懂项目

一句话：办公楼白领的「团体订餐」小程序——每天一栋楼共享一个「一饭四菜」套餐，4 家供应商各出一菜，在集散中心打包装箱，货拉拉送到楼下，楼里的团长取餐分发；平台赚差价，团长赚佣金。

节点时间

截单（关键锚点 1）T-1 24:00
供应商出餐 → 送集散中心T 日 06:00–09:30
货拉拉叫车（线下）T 日 10:00
兼职打包完成T 日 11:00

C11佣金个税与出款通道 / 供应商结算周期 ① 团长佣金个税 ＝ 走「灵活用工平台」：平台对公账户 → 灵活用工平台 → 团长本人；个税由灵活用工平台代扣代缴并完税，灵活用工平台向平台开具服务发票。产品形态不变（佣金计算 → 计入佣金余额 → 团长提现），仅出款通道抽象为 PayoutChannel：一期「生成打款批次 + 清单导出 + 回执登记」，二期接灵活用工平台 API。
② 供应商 / 集散中心结算周期 ＝ 日结：系统 T+1 02:00 生成应付结算单，财务按日付款并登记回单；对公账户信息可后置收集，不阻塞开发（ab_supplier 银行字段允许为空，付款登记支持「收款方式」备注）		 ① 团长为自然人 + 高频小额，灵活用工平台一次解决「代发 + 个税代扣 + 完税凭证」三件事，且不再依赖微信支付「商家转账到零钱」产品权限（少一项申请/审核依赖，上线更快）。
② 供应商侧现网已是日结，系统按日生成应付单即可，不改造既有财务习惯；对公账户只影响付款执行环节，不影响系统建模与开发排期		 PRD §6.2 / §6.4 / §七·风险 / 合规清单 §4·§5·§6·§8 / 账号资源 §3.2·§3.3 / 接口规范 §4.4 + W3 / 状态机 §3·§5 / 里程碑 R1·R2 / 原型 P16·P18 / 脚手架 PayoutChannel 全部改毕

目标：让「用户下单 → 截单 → 出餐 → 送达 → 取餐确认 → 分账」这条链在原型上无断点、无歧义。
