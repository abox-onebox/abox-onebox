## 一、裁定摘要

### 1.1 四条裁定（2026-09-16 用户逐条确认）

| # | 议题 | 裁定 | 理由 |
| --- | --- | --- | --- |
| 1 | 用户退款是否冲减供应商应付 | **不冲减** | 半成品在出餐日已交付；退款发生在交付之后，属 ABox 自身经营风险 |
| 2 | 采购应付的计费基数 | **实收量**（`actual_quantity`） | 采购的本质是「收多少付多少」；短送自动少付，无需人工对账 |
| 3 | 应付对象边界 | **仅供应商采购款** | 场所摊销 / 打包人工 / 配送费是 ABox 自身成本（房租、工资、运费），不是「应付给谁」 |
| 4 | C9 等式「场地费」科目 | **保留科目、改语义** | `siteFee`：复用供应商场地·默认 0 → **ABox 自有持证场所摊销**，默认值不再为 0 |

### 1.2 两条不变量（无需讨论，直接生效）

- **I1 · 供应商端不得出现终端定价信息**：售价 ¥25.80、佣金费率/金额、毛利、成本合计，一律不出现在供应商端任何页面与接口出参中。
  理由：B2B 采购关系下供应商只应知道「我的价 × 我的量」；暴露完整利润结构会让下一轮谈价失去筹码。
- **I2 · 等式闭合性不变**：售价 = 供价 + 场地费 + 打包人工 + 配送费 + 佣金 + 毛利，恒应闭合；
  `assertSettlementClosed()` 继续作为对账校验工具。

## 二、结算等式与科目语义

### 2.1 等式（结构与锁定项均不变）

```
售价 ¥25.80（锁定）
  = 供应商供价 + 场地费 + 打包人工 + 配送费 + 团长佣金 + 经营毛利（结果值）
```

锁定项：售价 · 4 级佣金费率（8/9/10/12%）· 等式结构 · 退款按同结构反向回退（余额与佣金侧）。
可配置项：供价（逐菜协商）· 场地费（实际摊销）· 打包人工 · 配送费。

### 2.2 科目语义对照（旧 → 新）

| 科目（字段名不变） | 旧语义 | **新语义** | 是否进应付单 |
| --- | --- | --- | --- |
| `supplierTotal` 供应商供价 | 4 家供应商**分账**所得 | **半成品采购款** = 逐菜协商采购价 × 实收量 | ✅ **是**（唯一） |
| `siteFee` 场地费 | 集散中心**复用合作供应商场地** → 默认 ¥0 | **ABox 自有持证场所摊销**（月租金/物业等 ÷ 月产量） | ❌ 否 · 内部成本 |
| `packingLaborFee` 打包人工 | 平台**雇佣兼职**打包 | **ABox 加工场所用工**（工资 / 劳务报酬） | ❌ 否 · 内部成本 |
| `deliveryFee` 配送费 | 安排**货拉拉**送货 | **ABox 履约配送**（自有骑手成本或外包运费） | ❌ 否 · 内部成本 |
| `commission` 团长佣金 | 灵活用工平台代扣代缴 | **不变** | ⭕ 独立通道（自动结算，C11） |
| `platformGrossProfit` 平台毛利 | 结果值 | 结果值；**中文口径改称「经营毛利」**（字段名不动，避免牵动 M1/M2 已消费代码） | ❌ 否 |

### 2.3 ⚠️ 毛利口径的重要变化

旧口径下 `siteFee / packingLaborFee / deliveryFee` **默认全为 0**，因此「毛利 ¥9.22」实际是**未扣履约成本的上限值**，不是真实利润。

自营下三项均有真实成本，因此必须区分两个数（`calcSettlement()` 只产出**一个**结果值，下表是同一公式取不同输入时的两种含义）：

| 数 | 算法 | 何时成立 |
| --- | --- | --- |
| **经营毛利**（结果值） | 售价 − 采购款 − **场地摊销 − 打包人工 − 配送费** − 佣金 | 三项履约成本**已由运营登记真实值**时 —— 此时它就是真实净利 |
| **上限毛利**（同一公式） | 同上，但三项取默认 0 | 履约成本**尚未登记**时的占位值，**系统性高于**真实净利 |

> ⭐ **结论：毛利的可靠性完全取决于三项履约成本是否登记了真实值。**
> 运营未登记时，看板显示的「经营毛利」会被**系统性高估** —— 这是 D47–D50 数据看板必须显式提示的点
> （例如在毛利卡上标注「履约成本未登记，当前为上限值」）。
> 本系统**不出这三项的付款单**（§三），但它们**必须进等式**，否则毛利没有意义。

## 三、应付对象与单据边界

### 3.1 三个资金出口，只有一个是「应付单」

| 出口 | 对象 | 形态 | 通道 |
| --- | --- | --- | --- |
| **① 供应商采购款** | 4 家半成品供货方 | **应付结算单**（`ab_supplier_share`） | 人工对公转账 + 回单号（C10 不变）+ **索取发票** |
| ② 团长佣金 | 团长（自然人） | 佣金流水 + 提现单（`ab_withdraw`） | 灵活用工平台代扣代缴（C11 不变，自动结算） |
| ③ 内部履约成本 | 房东 / 员工 / 配送方 | **不进本系统**（走租赁合同、工资表、运费结算） | 会计科目，仅在成本核算与看板体现 |

### 3.2 `payee_type` 值域

| 值 | 状态 | 说明 |
| --- | --- | --- |
| `supplier` | ✅ **唯一有效值** | 半成品供货方 |
| `distribution_center` | ⛔ **冻结** | 历史数据保留可读；**新单不再产生**。自营下加工场所属 ABox，付场地费给自己在财务上无意义 |

## 四、计费基数与出单规则

### 4.1 计算公式

```
应付金额 amount = quantity（实收量） × unit_price（逐菜协商采购价）
```

| 元素 | 来源 | 落库字段 |
| --- | --- | --- |
| 实收量 | `ab_supplier_dish_daily.actual_quantity` | `ab_supplier_share.quantity` |
| 采购单价 | ⭐ **`ab_supplier_dish_daily.unit_price`**（出餐计划生成时**冻结**的协商价快照）；该值为空时才回落到 `ab_dish.cost_price` | `ab_supplier_share.unit_price` |
| 出餐日 | `produce_date` | `ab_supplier_share.meal_date` |
| 应付生成日 | 跑批执行日（T+1） | `ab_supplier_share.share_date` |

> ⭐ **单价取「冻结快照」而非出单时刻的 `ab_dish.cost_price`**（本文档 §4.1 初版的写法已按此修正）：
> 出餐计划一旦生成即**冻结**（M3-8 的核心纪律），计划里的 `unit_price` 就是当日对供应商的
> **承诺价**。若事后有人改了菜品采购价、结算时按新价付，就会出现「T 日按 ¥7.50 交货、
> 结算按 ¥8.00 付」—— 供应商对账时必然拒绝。**谁被冻结，就按谁结算。**
> 实现见 `modules/finance/supplier-share.service.ts` 的 `unitPriceOf()`；e2e §21 用
> 「夹具价 ≠ 菜品成本价」的方式断言了这一点。

**实收量的定义**（沿用 M3-8 S2 语义）：供应商在出餐确认时申报的实送份数；**未申报则等于计划量**（视为足额送达）。
→ 因此「不申报」= 默认足额，「申报短送」= 少付，供应商有义务主动申报短送。

### 4.2 出单粒度

`(供应商, 菜品, 出餐日)` 一行 —— 与 `ab_supplier_share.dish_id` 既有设计一致，便于逐菜对账。

### 4.3 不出单的三种情形

| 情形 | 处理 | 理由 |
| --- | --- | --- |
| 实收量 = 0（计划量本为 0，或整菜未送） | **不生成行** | 与 M3-8「只生成 `planQuantity > 0`」同源，避免单上长出一串 0 元行 |
| 该日该菜品**未全部确认完成**（父表 `status != 'done'`） | **fail-closed，不出单** → 进「未出单异常清单」+ `reason`，人工处理 | 此时 `actual_quantity` **只覆盖已确认的明细**（见 `supplier.service.ts` 的 `confirmedQty` 重算逻辑）。按它出单 → **少付**；按计划量补齐 → **多付**。两种猜法都在钱上出错，故不猜 |
| 供应商资质异常（`can_serve = false`） | 不出单 + 标记资质异常 | 资质未核验期间的供货不应进入结算 |

> ⚠️ 第 2 条为**本文档代定**（fail-closed），与 M3-8 的 `50009`、D41/D42 的 `40014` 同一纪律：**缺关键输入时不猜默认值**。
> 若业务上更倾向于「按计划量补齐、差异下期调整」，可推翻本条并改走差异行方案。

### 4.4 幂等

同一 `(供应商, 菜品, 出餐日)` 只应存在**一行有效 `type='normal'`** 记录。
跑批需支持重跑（迟到确认后的重跑可补上先前因 fail-closed 跳过的行），键冲突时不重复出单。

## 五、退款与纠错的资金处理

### 5.1 用户退款：不冲减供应商应付（裁定 1）

- 半成品在**出餐日（T）当日已交付**并被 ABox 使用；退款发生在交付之后。
- 因此退款**不改变** ABox 对供应商的采购义务：钱照付。
- **后果**：退款那部分份数的采购款已支出而收入已退回 → **经营毛利可能为负**。
  这是**经营风险的正常承担**，不是系统缺陷，看板上应作为正常情形呈现。

### 5.2 `type='reversal'` 重新定义（不再由退款触发）

| | 旧用途 | **新用途** |
| --- | --- | --- |
| 触发源 | 用户退款 → 反向结算 | **应付单生成后发现算错**（数量/单价录错、重复出单） |
| 形态 | 冲减未付款行 / 写反向流水挂下期 | 写负向行 `origin_id` 指向原行，**挂下一期抵扣** |
| 原行处理 | 未付款行扣减至 0 则置 `reversed` | 已付款行**不得改写**（钱已转出，改写即篡改已发生事实） |

### 5.3 不受影响的部分

- **团长佣金回退**：退款仍按原口径冲减佣金（`ab_commission` 写 `type='reversal'` 负行），
  这是 ABox ↔ 团长 的关系，与供应商无关 → **M3-3 该部分实现保持不动**。
- **用户余额回退**：`ab_balance` 扣减（允许为负）不变。

## 七、可见性与对账纪律

### 7.1 供应商端允许/禁止展示

| ✅ 允许 | ⛔ 禁止（不变量 I1） |
| --- | --- |
| 我的菜品 · 我的协商单价 | 套餐售价 ¥25.80 |
| 我的计划量 / 实收量 | 佣金费率与金额 |
| 应付我的金额 · 付款状态 · 回单号 | 毛利、成本合计、其他供应商的报价 |

### 7.2 对账依据

- 供应商看到的「实收量」= `actual_quantity`，其确认动作留痕 `confirmed_at` + `confirmed_by`（运营账号 id）。
- 供应商若有异议：**以确认时间戳与 `remark` 为准**（S2 短送留痕即对账凭据）。
- 对账单与银行回单号一一对应，回单号为付款完成的唯一凭证（`payment_voucher_no`）。

> 本节由「开工前预告」转为**实装对照**：路径与入参与预告一致者直接采用，**不一致者在此登记偏离与实际口径**。

| 用途 | 方法与路径 | 要点 |
| --- | --- | --- |
| 应付单列表 | `GET /admin/supplier-shares?date=&supplierId=&status=&keyword=&page=` | 分页；金额出参一律整数分（`Fen`）；`summary` 按**同一过滤条件的全量**统计（不受分页影响），并按 `pending` / `paid` 拆分 |
| 生成应付 | `POST /admin/supplier-shares/generate` —— **或**跑批 `supplier-share.task`（T+1 02:00，**只生成不拨款**），两者**共用同一执行口** | 幂等走**软层**（同键已有有效 `normal` 行即跳过）；fail-closed 项进异常清单；`created[]` 回填 `id`（运营要能直接对它登记付款） |
| 付款登记 | `POST /admin/supplier-shares/{id}/payment` | `paymentVoucherNo` 必填（缺 → `50013`）+ `invoiceNo` 可选 → `status=success`；**仅 `pending` 可登记**（否则 `50012`）；同一回单号不得用于两笔 |
| 未出单异常清单 | `GET /admin/supplier-shares/exceptions?date=`（`date` **必填**） | 列 `reason`：`not_started` / `incomplete` / `actual_missing` / `license_invalid` / `zero_quantity`；已出单的行会被过滤 |
| 供应商自查 | `GET /supplier/settlement?date=` | **只读自己的**；由 token 内 `supplierId` 收窄，**不支持传入 `supplierId`**；出参含 `pendingAmountFen`（该日）与 `pendingTotalAmountFen`（**不限日期**合计） |

**实施期修正（与预告的偏离）**

| # | 项 | 预告 | 实装 | 为什么 |
| --- | --- | --- | --- | --- |
| 1 | 出单价来源 | 未明确（§4.1 初稿写「`ab_dish.cost_price`」） | **`ab_supplier_dish_daily.unit_price` 冻结快照优先**，为空才回落 `ab_dish.cost_price` | 出餐计划生成时已冻结协商价；若按出单时刻的成本价付，会出现「T 日按旧价交货、结算按新价付」 |
| 2 | 幂等实现 | 「键冲突不重复出单」（原设想 DB 唯一索引） | **软层判定**，不建唯一索引 | 本表还要容纳 `type='reversal'` 负行，同键正负两行是**合法冲销** —— 唯一索引会误伤它 |
| 3 | `50014` | 预留「该日出餐确认未完成，无法出单」 | **取消（号位释放）** | 该情形**不是一次失败**，而是「这天还缺输入」的常态待办：转人工进异常清单，逐条给原因。做成错误码只会让运营看到「出单失败」却看不到「哪几家没确认」——而那才是他唯一能执行的线索 |
| 4 | 管理端路径 | `/admin/finance/supplier-shares` | **`/admin/supplier-shares`** | 资源式挂模块根，与 `/admin/suppliers` 一致；**前缀仍是 `/admin/*`，鉴权依据不变** |

- `50012` 应付单不存在或当前状态不可操作（含已付款再登记 = 重复出款）
