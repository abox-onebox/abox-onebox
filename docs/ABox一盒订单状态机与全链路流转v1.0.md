## 一、状态定义

### 1.1 主状态机（11 态 = 正常 7 + 异常 4）

| 状态 | 中文 | 语义 | 终态 |
| --- | --- | --- | --- |
| `pending_pay` | 待支付 | 下单未付款（30 分钟内有效） | — |
| `paid` | 已支付 | 已付款，等待截单 | — |
| `cut_off` | 已截单 | 截单锁定，等待出餐 | — |
| `cooked` | 已出餐 | 供应商确认出餐完成 | — |
| `delivering` | 配送中 | 货拉拉发出 | — |
| `delivered` | 待取餐 | 11:30 送达办公楼 | — |
| `completed` | 已完成 | 团长确认 / 14:00 自动确认 + 佣金入账 | ✅ |
| `cancelled` | 已取消 | 截单前取消 / 超时未支付 | ✅ |
| `refund_applying` | 退款申请中 | 团长代退申请已提交，待平台审批 | — |
| `refunding` | 退款中 | 审批通过，微信退款处理中 | — |
| `refunded` | 已退款 | 退款到账 + 反向分账完成 | ✅ |

| 主状态 | 用户端（5 态展示） | 团长端（6 态展示） | 后台（8 态展示） |
| --- | --- | --- | --- |

| `paid` | **待出餐** | 待出餐 | 已支付 |

| `cooked` | **待出餐** | 已出餐 | 已出餐 |
| `delivering` | 配送中 | 配送中 | 配送中 |
| `delivered` | 待取餐 | 待取餐 | 待取餐 |
| `completed` | 已完成 | 已完成 | 已完成 |
| `cancelled` | 已取消（异常区） | 已取消 | 已取消 |

## 二、状态迁移表

| # | 从 | 到 | 触发者 | 触发条件 | 副作用（事务内） |
| --- | --- | --- | --- | --- | --- |
| T1 | — | `pending_pay` | 用户 | 下单成功（截单窗口内、份数合法） | 写 `ab_order`；冻结余额（如有） |
| T2 | `pending_pay` | `paid` | 系统 | 微信支付回调验签成功 | 写 `ab_payment_log`；扣减冻结余额为实扣；**订阅消息：支付成功** |
| T3 | `pending_pay` | `cancelled` | 系统 | **30 分钟未支付** | 解冻余额；无需退款（未收款） |
| T4 | `pending_pay` / `paid` | `cancelled` | 用户 | 自助取消（**仅截单前**） | 若 `paid`：发起原路退款（系统自动）；解冻/退余额 |
| T5 | `pending_pay` | `cancelled` | 系统 | **T-1 24:00 截单** 时兜底取消 | 同上（批量，`cutoff.task`） |
| T6 | `paid` | `cut_off` | 系统 | **T-1 24:00** 截单锁定 | 汇总份数 → 推送 4 家供应商备料量；不可逆 |
| T7 | `cut_off` | `cooked` | 供应商 | 出餐确认（**须 ≤ 09:30**） | 写 `ab_supplier_dish_daily.produced_at`；**订阅消息：出餐提醒** |
| T8 | `cooked` | `delivering` | 运营/系统 | 货拉拉发出（运营在后台标记，或 `delivery-generate.task` 后由配送单驱动） | 更新 `ab_delivery_record.status='delivering'` |
| T9 | `delivering` | `delivered` | 运营 | 11:30 送达办公楼 | 写 `ab_delivery_record.arrived_at`；**订阅消息：取餐通知（团长）** |
| T10 | `delivered` | `completed` | 团长 | 手动确认收货并分发（幂等） | 写 `ab_commission`（按团长等级）；余额账户入账 |
| T11 | `delivered` | `completed` | 系统 | **T 日 14:00** 自动确认兜底 | 同上（批量，`auto-confirm.task`） |
| T12 | `cut_off`/`cooked`/`delivering`/`delivered`/`completed` | `refund_applying` | 团长 | **代退申请**（C6 第一段） | 写 `ab_refund`（`status='applying'`）；**不退款、不回退分账**；通知客服 |
| T13 | `refund_applying` | `refunding` | 运营 | **后台审批通过**（C6 第二段） | 调微信退款 API → 写 `ab_refund.status='refunding'` |
| T14 | `refunding` | `refunded` | 系统 | 微信退款回调成功 | **反向分账**（见 §5.3）；扣减佣金；**订阅消息：退款结果（必推）** |
| T15 | `refund_applying` | （回原状态） | 运营 | **后台驳回** | `ab_refund.status='rejected'`；**订阅消息：驳回原因** |
| T16 | 任意非终态 | `cancelled` | 运营 | 强制退款（M32-05） | 同上 T4；**必须写 `ab_operation_log`** |

### 2.1 状态机守则

1. **单向为主**：T1→T11 为主干，除退款分支外**不可逆**。
2. **终态封闭**：`completed` 只能通过退款分支"降级"为 `refunded`（佣金冲销），不可回到流转态。
3. **截单是硬闸**：T6 之后，**任何用户侧写操作**（改数量、改地址、自助取消）一律拒绝（`30003`）。
4. **幂等要求**：T10 / T11 / T13 / T14 均须幂等——以 `(order_id, action)` 或微信单号做键，重复触发返回首次结果。
5. **状态变更必须落日志**：每次迁移写 `ab_operation_log`（`target_type='order'`），记录 `from_status → to_status`、操作者、时间、来源（`system` / `user` / `leader` / `admin`）。

## 三、时间轴事件（一个自然日的完整生命周期）

```
T-1 14:00  ┃ meal-publish.task        开团：次日套餐上架，用户可下单
           ┃                         （原型 P1 can_order=true）
T-1 24:00  ┃ cutoff.task   ⚠️锚点1    截单：
           ┃                         ① pending_pay → cancelled（批量）
           ┃                         ② paid → cut_off（锁定）
           ┃                         ③ 汇总各菜品份数 → 推送 4 家供应商
T 日 00:30 ┃ delivery-generate.task    生成次日配送单 ab_delivery_record
T 日 06:00 ┃ （线下）                  供应商开始出餐
T 日 09:30 ┃ （截止）                  出餐截止（cook-confirm 逾期标 warning）
T 日 09:30 ┃                         集散中心 4 菜到齐 → 兼职打包装箱
    11:00  ┃ （线下）                  打包完成
T 日 10:00 ┃ （线下）                  货拉拉叫车
T 日 11:00 ┃ （线下）                  装车发出 → delivering
T 日 11:30 ┃ 系统                     送达 → delivered + 推送团长取餐通知
    11:30  ┃                         取餐窗口开启
    12:30  ┃                         取餐窗口关闭
T 日 14:00 ┃ auto-confirm.task ⚠️锚点2 自动确认收货：
           ┃                         ① delivered → completed（批量）
           ┃                         ② 写 ab_commission（按团长等级 8/9/10/12%）
T+1 02:00  ┃ commission-settle.task    佣金入账：计入团长佣金余额（提现走灵活用工代发·C11）
     02:00 ┃ supplier-share.task       生成供应商应付结算单（不拨款，财务对公转账）
T+1 04:00  ┃ reconciliation.task       与微信支付每日对账
```

### 3.1 定时任务清单（与代码落点对应）

| 任务 | 触发时间 | 幂等键 | 职责 |
| --- | --- | --- | --- |
| `meal-publish.task` | T-1 14:00 | `meal_date` | 套餐上架、开团 |
| `cutoff.task` | T-1 24:00 | `meal_date` | 截单：取消未支付 + 锁定已支付 + 推备料 |
| `delivery-generate.task` | T 日 00:30 | `meal_date` | 生成配送单 |
| `auto-confirm.task` | T 日 14:00 | `meal_date` | 自动确认收货 + 计算佣金 |
| `commission-settle.task` | T+1 02:00 | `meal_date` | 佣金入账到团长余额（提现走灵活用工平台代发 · C11） |
| `supplier-share.task` | T+1 02:00 | `meal_date` | 生成供应商 / 集散中心**应付结算单**（不拨款） |
| `reconciliation.task` | 每日 04:00 | `date` | 对账 |
| `leader-expire.task` | 每日 03:00 | `date` | **见习团长 30 天未促单 → 取消资格（C2）** ⭐ |

> ⚠️ **`leader-expire.task` 为新增项**：C2 明确"见习 30 天未促单自动取消资格"，而《目录结构 v2.0》`tasks/` 未列此任务——本文件补齐，实施时需一并加入 `tasks/` 目录。
> 判定口径：`level='trainee' AND status='active' AND DATEDIFF(NOW(), last_order_at) > 30` → `status='expired'`，并推送提醒。

## 四、退款全链路（C6 三段式）

### 4.1 硬口径

| 时段 | 用户可否自助退 | 路径 |
| --- | --- | --- |
| 截单前（`pending_pay` / `paid`） | ✅ 可 | 用户端「取消订单」→ 系统自动退款 |
| 截单后（`cut_off` 及以后） | ❌ **不可** | 用户端仅显示「联系团长/客服」→ 团长发起代退申请 → 后台审批 |

### 4.2 三段式流程

```
┌─ 第一段 · 用户发起 ────────────────────────────────────────┐
│ 用户端 U11 /orders/{no}/cancel  →  截单后返回 40004        │
│ 端上展示「截单后无法自助退款，请联系团长协助」+ leaderContact │
└────────────────────────────────────────────────────────────┘
                        ↓
┌─ 第二段 · 团长代退申请（L7）──────────────────────────────┐
│ POST /orders/{no}/refund-apply  { reasonType, reason }      │
│  → ab_refund：status='applying'，order.status='refund_applying'│
│  → ⚠️ 此时【不退款、不回退分账】，仅登记                      │
│  → 通知运营后台（待审批队列 D40）                             │
└────────────────────────────────────────────────────────────┘
                        ↓
┌─ 第三段 · 后台审批（D41 / D42）───────────────────────────┐
│ 通过 D41：                                                  │
│   ① 调微信退款 API（原路退用户）                            │
│   ② ab_refund：applying → approved → refunding              │
│   ③ 回调成功 → refunded                                     │
│   ④ 反向分账（见 §5.3）                                     │
│   ⑤ 若订单已 completed → 冲销 ab_commission（写反向流水）    │
│   ⑥ 推送微信订阅消息（退款结果，**必推**）                   │
│ 驳回 D42：                                                  │
│   ① ab_refund：applying → rejected                          │
│   ② 订单回到发起前状态（refund_applying → 原状态）           │
│   ③ 推送驳回原因给用户                                       │
└────────────────────────────────────────────────────────────┘
```

### 4.3 边界规则

| 场景 | 处理 |
| --- | --- |
| 用户重复申请 | `40008`（`(order_id, status in applying/approved/refunding)` 唯一） |
| 截单前用户自助退 | 走 T4，**不经**团长与审批 |
| 强制退款（运营） | 走 D11，跳审批直接执行，**必写操作日志 + 原因** |
| 已出餐后退款 | 允许（如品质问题），分账按 §5.3 回退 |
| 部分退款 | **MVP 不支持**（按整单退），二期扩展 |
| 退款到账时长 | 微信侧 1–3 个工作日；系统状态即时置 `refunded`，文案注明到账时间 |

## 五、分账与结算（C9 · 2026-09-14 定案）

### 5.1 单份 ¥25.80 结算终稿

| 收款方 | 金额/份 | 口径 | 触发 |
| --- | --- | --- | --- |
| 4 家菜品供应商 | **¥14.00** | 按各菜品**成本单价**（如红烧肉 ¥7.50） | **人工对公转账 · 日结**（T+1 生成应付，按日付款） |
| 集散中心 | **¥5.00** | 米饭 ¥2.00 + 打包 ¥3.00（`ab_config` 可调） | **人工对公转账 · 日结**（同上） |
| 团长佣金 | **¥3.10** | 按实发份数 × 等级费率（首席 12% = ¥3.096） | **系统自动结算**：T 日 14:00 计入余额 / T+1 起可提现（**灵活用工平台代发 + 代扣个税** · C11） |
| 平台毛利 | **¥3.70** | 留存 | — |
| **合计** | **¥25.80** | ✅ 闭合 | — |

### 5.2 结算时点

| 动作 | 时点 | 说明 |
| --- | --- | --- |
| 佣金**计算** | T 日 14:00 | 订单 `completed` 时立即写 `ab_commission` |
| 佣金**入账** | T+1 02:00 | 计入团长**佣金余额**；提现走**灵活用工平台代发**（代扣个税 · C11） |
| 供应商**应付生成** | T+1 02:00 | 系统按菜品成本单价 × 实发份数生成**应付结算单** |
| 供应商**付款** | **按日（日结 · C11）** | **人工对公转账**（财务在网银执行，系统登记回单号；对公账户可后置收集） |

### 5.3 退款反向结算

**原则**：**已发生的结算与付款必须「反向冲销」，不得改写原记录。**

| 项目 | 退款处理 |
| --- | --- |
| 供应商 ¥14.00 | **冲减应付**：未付款直接冲减；已付款写反向 `ab_supplier_share`（`type='reversal'`），下期抵扣 |
| 集散中心 ¥5.00 | **冲减应付**（同上） |
| 团长佣金 | **回退**（写反向 `ab_commission`，金额取负） |
| 平台毛利 ¥3.70 | **留存**（不参与回退） |

> 与 ER `ab_supplier_share` / `ab_commission` 的设计一致：两张表均为**流水表**，反向操作以**新增负向流水**表达，保留完整审计链。**供应商 / 集散中心的付款由财务人工执行**，故「冲减」体现在**应付单**上，而非支付通道。

### 5.4 应付状态机（`ab_supplier_share.status` · 供应商 / 集散中心）

```
pending ──付款登记(D37)──> success（已付款）
   │
   ├──登记异常 ──> failed ──重新登记(D37)──> pending
   │
   └──订单退款 ──> reversed（新增反向流水后，原记录置 reversed）
```

## 六、异常与边界处理

| 场景 | 处理策略 |
| --- | --- |
| 支付回调延迟到账（>30min） | 订单已 `cancelled` 时回调到达 → 自动原路退款 + 告警 |
| 供应商未在 09:30 出餐 | 订单**状态不回退**，后台标 `warning` 提示运营介入（原型 P30 口径） |
| 团长失联不确认 | 14:00 自动确认兜底（无需团长配合） |
| 团长中途停用 | 订单归属不变，取餐由运营协调；新订单走新团长 |
| 货拉拉延误 | 系统只记录 `arrived_at`，不调度；延误不影响状态机 |
| 余额支付后取消 | 退回**余额**（不是微信），走 `ab_balance_log` 正向流水 |
| 佣金入账失败 | `failed` → 告警 + 后台重试（D35），不阻塞订单 `completed` |
| 集散中心停用 | 软删（D32）；已有分配继续走完当日流程 |

## 八、与原型页面的口径对照（防止实现漂移）

| 原型页 | 状态机相关口径 | 一致性检查点 |
| --- | --- | --- |
| P5 订单详情 | 时间线 6 节点（已支付→已截单→已出餐→配送中→送达→已完成） | 与 §三 时间轴一致 |
| P13 订单明细 | 退款走「发起代退申请 → 待运营审批 → 实际退款」三段 | 与 §4.2 一致 |
| P14 退款/异常处理 | 团长侧无「直接退款」按钮 | 与 C6 一致 |
| P15 取餐确认 | 份数按**实发**计（剔除已退款） | 与 §5.1 佣金基数一致 |
| P30 订单中心 | 出餐超时标 `warning` 而**不改状态** | 与 §六 一致 |
| P31 订单详情 | 时间线 6 步含「已出餐 → 集散中心 09:30–10:00」 | 与 §三 一致 |
| P34 财务结算 | 退款反向结算 = 供 + 集散 冲减应付 + 佣金冲销，毛利留存 | 与 §5.3 一致 |
