## 一、业务全景

### 1.1 业务模型

```
每日一套餐（4 道菜 + 1 米饭）
  ├─ 4 道菜由 4 家供应商各出 1 道（前期小单量可同供应商出多菜）
  ├─ 供应商出餐送到集散中心（集散中心也是某供应商，可同时出餐）
  └─ 集散中心兼职打包 → 货拉拉送办公楼 → 团长取餐分发
```

### 1.2 核心业务时序

```
T-1 14:00   ──── 系统开启次日套餐预订
                团长开始分享链接 → 用户下单 + 微信支付

T-1 24:00   ⚠️ ── 系统截单（关键锚点 1）
                锁定订单 → 推送供应商备料通知

T 日 06:00-09:30 ── 供应商出餐 → 送集散中心
                同一供应商每天做同一道菜，送到多个集散中心

T 日 09:30-11:00 ── 集散中心 4 菜到齐 → 兼职打包装箱

T 日 10:00   ──── 货拉拉叫车（线下）

T 日 11:00   ──── 打包完成 → 装车

T 日 11:00-11:30 ── 货拉拉配送中

T 日 11:30  ⚠️ ── 货拉拉送达办公楼
                小程序推送"取餐通知"给团长

T 日 11:30-12:30 ── 团长取餐窗口
                团长下楼取餐 → 分发给成员

T 日 14:00  ⚠️ ── 自动批量确认收货 + 结算团长佣金（关键锚点 2）
                未在 14:00 前手动确认的订单全部自动确认

T+1 日 02:00 ──── 财务跑批
                供应商应付结算（人工）+ 团长佣金（自动）
```

### 1.3 4 大角色

| 角色 | 形态 | 关键诉求 |
| --- | --- | --- |
| **用户**（C 端员工） | 微信小程序 | 简单下单、看今天吃啥、看取餐状态 |
| **团长**（按办公楼） | 小程序内嵌 | 分享链接、收集订单、确认收货、查佣金 |
| **商家**（供应商） | Web 后台 | 看明日订单、确认出餐、查结算 |
| **平台运营** | Web 后台 | 套餐编排、订单管理、财务结算、数据看板 |

> ⚠️ **无楼长角色**，团长兼任取餐分发。

## 二、关键业务规则

### 2.1 角色规则

| 规则 | 说明 |
| --- | --- |
| **用户注册** | 仅微信授权即可，**无需手机号、无需地址**（跟随团长） |
| **团长注册** | 需要手机号 + 地址信息（接收通知用） |
| **团长取餐** | 团长亲自下楼取餐，再分发给自己楼栋的成员 |
| **集散中心** | 是某供应商；可同时出餐 + 提供场地打包 |

### 2.2 套餐规则

| 规则 | 说明 |
| --- | --- |
| **套餐规格** | 固定 1 米饭 + 4 道菜（不支持单点/加菜） |
| **每天每栋楼** | 一个套餐 |
| **套餐分配** | **运营人员手动灵活分配**（无循环约束） |
| **供应商-菜品** | 动态：前期一人多菜 / 后期一人一菜 |
| **供应商-每天** | 同一供应商每天生产同一道菜（送不同集散中心） |
| **4 道菜** | 可来自同一供应商（前期）或 4 家不同供应商（后期） |

### 2.3 时间规则

| 节点 | 时间 |
| --- | --- |
| 开团 | T-1 14:00 |
| 下单窗口 | T-1 14:00 ~ T-1 24:00 |
| 截单 | T-1 24:00 |
| 货拉拉叫车 | T 日 10:00 |
| 兼职打包完成 | T 日 11:00 |
| 送达办公楼 | T 日 11:30 |
| 取餐窗口 | T 日 11:30 ~ 12:30 |
| 自动确认收货 | T 日 14:00 |
| 财务跑批 | T+1 日 02:00 |

### 2.4 财务规则

| 规则 | 说明 |
| --- | --- |
| **套餐定价** | **统一定价 ¥25.80/份**（C1） |
| **团长佣金** | 订单总金额 × 团长等级费率（见习 8% / 正式 9% / 金牌 10% / 首席 12% · C2） |
| **佣金用途** | **提现到微信零钱 OR 余额消费**（下次订餐抵扣） |
| **结算时点** | T 日 14:00 订单确认收货时计算 |
| **佣金入账** | T+1 日 02:00 跑批计入团长佣金余额；提现走**灵活用工平台代发**（代扣个税 · C11） |
| **供应商结算** | 系统 T+1 02:00 生成**应付结算单**；**人工对公转账**付款（不走支付通道分账） |
| **退款** | T-1 24:00 截单前可自助退；**截单后不可自助退**，走「团长代退申请 → 后台审批 → 实际退款」三段式闭环（C6） |

## 五、订单状态机

```
            ┌──────────────┐
            │ pending_pay  │ (待支付)
            └──────┬───────┘
                   │ 支付成功 / 30min 超时取消
        ┌──────────┴──────────┐
        ▼                     ▼
   ┌─────────┐          ┌──────────┐
   │  paid   │          │cancelled │
   └────┬────┘          └──────────┘
        │ T-1 24:00 截单
        ▼
   ┌─────────┐
   │ cut_off │ (已截单，待出餐)
   └────┬────┘
        │ 供应商出餐完成
        ▼
   ┌─────────┐
   │ cooked  │ (已出餐，待配送)
   └────┬────┘
        │ 货拉拉发出
        ▼
   ┌───────────┐
   │ delivering│
   └────┬──────┘
        │ 11:30 送达办公楼
        ▼
   ┌──────────────┐
   │ delivered    │ (待取餐)
   └────┬─────────┘
        │ 团长取餐+手动确认 / 或 T 日 14:00 自动确认
        ▼
   ┌─────────┐
   │completed│ (已完成 + 佣金结算)
   └─────────┘

退款路径（C6 三段式闭环）：
  pending_pay / cut_off 之前 ──用户自助取消──> cancelled + 退款（系统自动）
  cut_off 之后 ──用户不可自助退（仅「联系团长/客服」）
              ──团长发起代退申请──> refund_applying（待审批）
              ──平台后台审批通过──> refunding ──> refunded（原路退款 + 佣金冲销 / 应付冲减）
              ──后台驳回──> 回到原状态（用户端可重新联系团长）
```

## 六、关键业务场景专项

### 6.1 截单控制（T-1 24:00）

- CronJob `cutoff-task` 在 T-1 24:00:00 触发：
  1. 批量将所有"待支付"订单置为"已取消" + 自动退款
  2. 锁定所有"paid"订单 → "cut_off"状态
  3. 按菜品汇总份数 → 推送 4 家供应商"明日预计出餐量"
- 前端倒计时仅展示，最终以下单接口返回的 `can_order: false` 为准

### 6.2 团长佣金结算（T 日 14:00 + T+1 日 02:00）

**计算时点：** T 日 14:00 自动确认收货时
- CronJob `auto-confirm-task` 在 14:00:00 触发
- 所有未手动确认的"delivered"订单批量置为"completed"
- 立即写入 `ab_commission` 流水（按团长等级费率 8/9/10/12% 计 · C2）

**入账时点：** T+1 日 02:00
- CronJob `commission-settle-task` 触发
- 佣金**计入团长佣金余额**（团长可选择余额消费抵扣，或发起提现）
- 提现由平台**灵活用工合作方代发**（**代扣个税后到账** · C11）；到账结果走订阅消息触达

### 6.3 余额账户机制

| 操作 | 流水 |
| --- | --- |
| 佣金入账 | `+commission` |
| 用户余额消费（下单时抵扣） | `-order` |
| 用户提现 | `-withdraw` |
| 提现失败回退 | `+withdraw_refund` |

**下单时余额使用规则：**
- 用户可在支付页选择"使用余额抵扣 X 元"
- 余额 + 微信支付 = 订单总金额
- 优先级：余额优先扣减，不足部分走微信支付

### 6.4 结算方案（2026-09-14 定案）

> **C9 结算口径（终稿）**：单份 ¥25.80 = 供应商 4 家合计 **¥14.00**（按菜品成本单价）+ 集散中心 **¥5.00**（米 ¥2 + 打包 ¥3）+ 团长佣金 **¥3.10**（首席 12%）+ 平台毛利 **¥3.70**。退款按「供 + 集散 + 佣金」**反向冲销**，平台毛利留存。

**定案口径：供应商 / 集散中心走人工对公转账，只有团长佣金由系统自动结算。**

| 收款方 | 金额/份 | 结算方式 |
| --- | --- | --- |
| 4 家菜品供应商 | ¥14.00 | **人工对公转账 · 日结**（平台对公账户 → 供应商公司账户，凭增值税发票；对公账户信息可后置收集） |
| 集散中心 | ¥5.00 | **人工对公转账 · 日结**（同上；集散中心即某供应商） |
| 团长佣金 | ¥3.10 | **系统自动结算**：T 日 14:00 计入佣金余额 → 团长提现（**灵活用工平台代发 + 代扣个税** · C11） |
| 平台毛利 | ¥3.70 | 平台留存 |

> **为什么不再需要微信分账**：供应商 / 集散中心退出分账后，分账接收方只剩团长一个且单笔 ≤ 12%，原「分账单笔 30% 上限 vs 供应商合计 54.3%」的冲突自动消解。系统对供应商只需**生成应付结算单 + 登记付款**，不做任何支付通道调用。
>
> **C11 补充（佣金出款通道 · 2026-09-14 定案）**：① 团长佣金个税走**灵活用工平台**（代发 + 代扣代缴 + 完税凭证），平台对公账户 → 灵活用工平台 → 团长本人，**团长到手为税后金额**；② **产品形态不变**（佣金计算 → 佣金余额 → 提现），仅出款通道抽象为 `PayoutChannel`，一期「生成打款批次 + 清单导出 + 回执登记」、二期接 API；③ 微信侧**不再需要「商家转账到零钱」**；④ **供应商 / 集散中心结算周期 ＝ 日结**，对公账户信息可后置收集（不阻塞开发）。
