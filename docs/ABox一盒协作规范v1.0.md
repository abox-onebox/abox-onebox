## 一、四条不可协商的原则

| # | 原则 | 含义 | 违反后果 |
| --- | --- | --- | --- |
| P1 | **文档优先** | 任何口径 / 数值 / 文案变更，**先改 `docs/`，再改代码**，同一 PR 内完成 | PR 直接打回 |
| P2 | **增量不重写** | 在既有 PRD / ER / 原型之上迭代，不得另起一版、不得推翻已裁决口径 | 需重走评审 |
| P3 | **不碰锁定项** | L1–L12 与 C1–C11 有异议时**先提问**，不得自行修改；确需变更走 §六 变更流程 | PR 直接打回 |
| P4 | **单一事实来源** | `docs/` 与代码冲突时**以 `docs/` 为准**；`docs/` 与原型冲突时以 `docs/` 为准 | 立即回改代码 |

> 这三处最容易踩：把 ¥25.80 改成别的数、把 4 级佣金拍平成单一比例、把截单从 T-1 24:00 挪走。**这三件事都已定稿。**
>
> **第 4 处新增（C9 · 2026-09-15 修订）**：把单份结算的**成本项写死**。供价须**逐供应商逐菜协商**、集散中心**复用供应商场地（默认 ¥0）**、打包人工与配送费**按实际发生**；**平台毛利是结果值，不是常量**。任何「写死某个成本数」的实现一律打回。

## 二、分支策略

```
main            ← 可发布分支，只接受来自 release/* 或 hotfix/* 的合并
 └── develop    ← 集成分支，日常合并目标
      ├── feat-<模块>-<简述>    功能开发
      ├── fix-<模块>-<简述>     缺陷修复
      ├── refactor-<简述>       重构
      └── docs-<简述>           文档
 └── release/vX.Y.Z   ← 发布准备（只允许改版本号 / 修 bug）
 └── hotfix/vX.Y.Z    ← 线上紧急修复，同时合回 develop
```

| 规则 | 说明 |
| --- | --- |
| 命名 | 小写 + 连字符，含模块名，如 `feat-order-refund-three-stage` |
| 生命周期 | 分支存活 ≤ 5 个工作日；长期分支必须拆 |
| 保护 | `main` / `develop` 开启保护：禁止直推、禁止强推、必须 PR、必须 CI 绿 |
| 同步 | 合并前先 `rebase develop`，保持线性历史 |

## 三、提交规范

采用 **Conventional Commits**，由 `commitlint` 强制校验（`.commitlintrc` → `commitlint.config.cjs`）。

```
<type>(<scope>): <subject>

<body>

<footer>
```

### 3.1 type 取值

| type | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 仅文档变更（含 `docs/` 口径回写） |
| `refactor` | 重构（不改外部行为） |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `build` | 构建 / 依赖 |
| `ci` | CI 配置 |
| `chore` | 杂项 |
| `revert` | 回滚 |

### 3.2 scope 取值（与模块对齐）

`mp`（小程序）· `admin`（后台）· `api`（后端）· `order` · `payment` · `finance` · `leader` · `supplier` · `meal` · `building` · `task` · `db` · `docs` · `deps` · `ci`

### 3.3 示例

```
feat(order): 下单支持幂等键，避免重复创建

- 新增 idempotent.decorator，以 (user_id, meal_assignment_id, key) 唯一
- 对应《接口规范 v1.0》U7 幂等约定

Refs: docs/ABox一盒接口规范v1.0.md#U7
```

```
fix(finance): 反向结算改为新增负向流水，不再改写原记录

依据《订单状态机 v1.0》§5.3：已发生的结算必须反向冲销。

Refs: C6 / C10
```

> **规则**：涉及口径变更的提交，footer 必须写 `Refs: <文档章节号>` 或 `Refs: C<n>`；否则评审无法追溯。

## 四、代码评审

### 4.1 PR 要求

| 项 | 要求 |
| --- | --- |
| 规模 | 单 PR ≤ 400 行有效变更（不含生成文件 / 锁文件）；超出必须拆分 |
| 描述 | 必须填写 `.github/pull_request_template.md` 全部自检项 |
| Reviewer | 至少 **1 人 Approve**（涉及资金 / 权限 / 状态机的变更需 **2 人**） |
| CI | 4 个作业（lint / typecheck / test / build）**全绿**方可合并 |
| 合并方式 | Squash merge，保留规范化的提交信息 |

### 4.2 评审关注顺序

1. **口径是否与 `docs/` 一致**（最优先，不一致直接打回）
2. 是否触碰锁定项
3. 状态机迁移是否合法（对照 §二 迁移表）
4. 幂等与并发（下单、确认收货、退款、结算必须幂等）
5. 金额计算是否用**整数分**、是否有浮点误差
6. 越权风险（`role` 过滤：供应商只能看自己）
7. 测试是否覆盖异常分支

### 4.3 评审 SLA

| 优先级 | 首次响应 |
| --- | --- |
| P0 阻塞线上 | 30 分钟内 |
| P1 阻塞他人 | 4 小时内 |
| P2 常规 | 1 个工作日内 |

## 五、环境与配置纪律

| 环境 | 用途 | 数据 |
| --- | --- | --- |
| `local` | 本地开发（docker compose） | 种子数据 |
| `test` | CI 自动测试 | 每次重建 |
| `staging` | 联调 / 验收 | 脱敏真实数据 |
| `production` | 线上 | 真实数据 |

**硬纪律**

1. **密钥一律走环境变量**，`.env` 严禁入库；`.env.example` 必须同步维护（新增变量必须同时补 example）。
2. 生产密钥只存放在发布平台的密钥管理中，**不得出现在聊天记录、PR、截图、文档**里。
3. 生产库禁止 `synchronize: true`；所有结构变更走 **TypeORM migration**，且必须写 `down`。
4. 迁移脚本不得包含破坏性 DDL（`DROP` / 改类型）而不附数据迁移方案。
5. 手机号等敏感字段**加密存储**（`common/utils/crypto.ts`），日志中脱敏。
6. 生产环境禁止打印完整订单号 + 用户标识的组合日志。

## 六、文档变更流程（口径怎么改）

```
发现口径问题
   ↓
① 提 Issue（模板：feature_request），说明触碰了哪一条 L/C
   ↓
② 由产品负责人裁决（用户本人 / 被授权人）
   ↓
③ 改 docs/ 对应文档 → 提升版本号 → 在「变更记录」写清变更行
   ↓
④ 提交 docs: 提交（单独一个 PR，便于追溯）
   ↓
⑤ 在代码 PR 中引用该文档章节号，实现同步
   ↓
⑥ 同步 ab_config 种子（若为运行期可配参数）
```

### 6.1 变更申请必填

| 字段 | 说明 |
| --- | --- |
| 涉及条款 | L__ / C__ / 无（新增） |
| 现状 | 当前文档怎么写 |
| 建议 | 改成什么 |
| 理由 | 为什么必须改（业务 / 合规 / 技术硬伤） |
| 影响面 | 端 / 页 / 表 / 接口 / 已上线数据 |
| 回滚代价 | 若改错如何回退 |

### 6.2 文档版本规则

`v主.次.修` —— 主版本：口径推翻级变更；次版本：新增章节 / 新裁决；修订：错别字、表述。

## 七、命名与技术规范

### 7.1 命名

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| 文件 / 目录 | kebab-case | `meal-card.vue`、`order.service.ts` |
| 组件 | PascalCase | `MealCard.vue` |
| 类 | PascalCase | `OrderService` |
| 变量 / 函数 | camelCase | `getOrderById` |
| 常量 | UPPER_SNAKE | `MAX_QUANTITY_PER_ORDER` |
| 数据库表 | `ab_<模块>_<实体>` | `ab_order_item` |
| 数据库字段 | snake_case | `team_leader_id` |
| 接口路径 | kebab-case | `/api/v1/set-meals` |
| 环境变量 | UPPER_SNAKE | `WXPAY_MCH_ID` |

### 7.2 数据约定（不得违反）

- 金额：`DECIMAL(10,2)`；**代码内一律先转整数分计算**，仅在展示 / 落库时转元
- 时间：`DATETIME(3)`，统一 **UTC+8**
- 每表必备：`id / created_at / updated_at / version`
- 软删除：`deleted_at`（禁止物理删除业务数据）
- 流水类表（`ab_commission` / `ab_supplier_share`）**只增不改**；反向操作用**负向流水**表达

### 7.3 前端纪律

- 设计 token 只写在 `styles/tokens.scss`（小程序端由 `uni.scss` 自动注入），**禁止散落硬编码色值**
- 后台必须覆盖 Element Plus 默认橙：警告色统一 `#C44536`
- 文案中的金额统一走 `formatYuan()`，禁止手写 `toFixed`

## 八、测试与质量门禁

### 8.1 必须写单测的场景

| 场景 | 原因 |
| --- | --- |
| 状态机迁移 | 非法迁移必须被拒绝（截单后不可自助取消） |
| 佣金计算 | 4 级费率 × 实发份数，金额必须精确 |
| 退款三段式 | 申请阶段**不得退款**、不得回退账务（⚠️ 2026-09-16 自营口径：退款本身也**不冲减供应商应付**） |
| 反向结算 | 负向流水金额正确、毛利留存 |
| 幂等 | 重复触发返回首次结果 |
| 权限 | 供应商越权访问他人数据必须 403 |

### 8.2 质量门禁（CI 四作业）

| 作业 | 命令 | 通过标准 |
| --- | --- | --- |
| lint | `pnpm lint` | 0 error、0 warning（`--max-warnings 0`） |
| format | `pnpm format:check` | 格式已符合 Prettier（**不要用 `pnpm format`**，那是就地改写） |
| typecheck | `pnpm typecheck` | 0 类型错误（含两个前端的 `vue-tsc`） |
| test | `pnpm test` | 用例**实际被执行**且全通过 —— 看输出里的用例数，不要只看退出码 |
| build | `pnpm build:api && pnpm build:admin && pnpm build:mp` | 三个端均构建成功 |

> ⚠️ **「假绿」防呆**：jest 配了 `--passWithNoTests`，"一个用例都没跑"也会返回成功。
> 判断标准是看输出里的 `Tests: N passed`，**N 必须 > 0**。
> 当前基线：`apps/api-server/test/unit/order-state-machine.spec.ts`，4 个用例（对应状态机 T1–T11 / C6 / 终态 / 退款分支）。
> 覆盖率 ≥ 70% 的门槛待业务代码落地后再纳入门禁（现状未达标，暂不阻断合并）。

### 8.3 DoD（完成的定义）

一个任务只有**同时**满足以下条件才算完成：

- [ ] 功能按 `docs/` 口径实现，无自行发明
- [ ] 类型检查 / lint / 单测本地通过
- [ ] 关键分支有单测
- [ ] 新增接口已出现在 Swagger
- [ ] 涉及口径变更时，`docs/` 已先改并同步
- [ ] PR 已 Approve 且 CI 全绿
- [ ] 已在 staging 自测通过

## 九、发布与回滚

| 环节 | 规则 |
| --- | --- |
| 版本号 | 语义化版本 `v主.次.修`，与 `docs/` 版本独立演进 |
| 发布窗口 | 试运营期：**周一至周四 14:00–17:00**（避开 11:30 取餐高峰与截单窗口） |
| 灰度 | 先发 `staging` → 验收 → 生产灰度 1 个办公楼 → 全量 |
| 发布前 | 数据库迁移已备份；回滚脚本已就绪；关键指标看板已打开 |
| 回滚 | 镜像回退 + 迁移 `revert`；**禁止**在生产手写 SQL 修数据（须走脚本 + 留痕） |
| 事故 | 触发 P0 → 立即在群里同步 → 30 分钟内给出止损方案 → 次日补复盘 |

**绝对禁发窗口**：`T-1 23:30–24:30`（截单）、`T 日 10:00–12:30`（配送取餐）。这两个窗口里系统必须保持稳定。
