一开工前：谁做什么

工程 开工前 5 分钟
  1. 在本机执行下面这条命令
  2. 等终端打出二维码与地址
  3. 把二维码/地址与身份分配发给测试人
cd abox-onebox
node scripts/local-test.mjs --seed --build
测试人 拿到地址后
  1. 手机连与电脑同一个 WiFi
  2. 扫二维码，或手输终端给的地址
  3. 登录时填分给自己的身份（见第二节）
http://<本机IP>:5180/　用户端
http://<本机IP>:5173/　运营后台
共同 开始前先对齐
  1. 这是内部环境，链接不外发、不拉外部用户
  2. 支付走的是模拟通道，不产生真实资金
  3. 今天的目标是攒问题，不是「全部跑绿」
发现问题 = 本清单最有价值的产出

二环境入口与身份

入口 地址 账号 / 身份
用户端 · 团长端 http://<本机IP>:5180/ 登录框填 dev:1001 这类标识，不需要真实微信
运营后台 http://<本机IP>:5173/ admin / admin123（超管）　finance / finance123　sanweiwu / supplier123
接口文档 http://<本机IP>:3000/docs 给工程看；测试人一般不用
健康检查 http://<本机IP>:3000/api/v1/health 页面打不开时先看这里
身份要一人一个，别共用
  • 同一个身份在同一天只能下一单（这是设计，不是故障）。两人共用 dev:1001，第二个人一定会被拦，然后被写成 bug。
  • 多人同时测：A 用 dev:1001（李明·首席 12%）· B 用 dev:1002（王芳·金牌 10%）· C 用 dev:1003（张磊·正式 9%）· D 用 dev:1004（赵静·正式 9%）· E 用 dev:1005（陈强·见习 8%）。
  • 如果你被提示「已提交过该日出餐的订单」——先确认是不是别人用了你的身份，再决定要不要记。

三用户端 / 团长端（手机，按顺序做完）

步骤 做什么 应该看到 不符时记什么
U1 打开首页 「明日」套餐卡片：售价 ¥25.80、一饭四菜、截单倒计时
U2 点进套餐详情 四个菜名与图片齐全；有送达信息（次日 11:30 送达本楼）
U3 下单：选份数 → 提交 提交后进入支付环节，金额 = ¥25.80 × 份数
U4 走完支付 模拟通道约 1 秒自动成功；订单状态变为已支付
U5 我的 → 订单列表 能找到这一单，状态已支付，出餐日为明日
U6 打开订单详情 金额、份数、出餐日、下单时间都在，且与 U3 一致
U7 同一天再下一单 应被拦下，提示已提交过该日出餐的订单 —— 拦住了才是对的
U8 回到订单详情 → 取消订单 受理成功、状态变为已取消/已退款；金额与 U3 一致
U9 溯源 能看到食材来源与加工场所信息
U10 切到团长 tab 有邀请入口、我的佣金、余额明细三个入口，都能打开
U11 把两个地方的余额对一遍
（历史踩过的坑，重点看）		 「我的」页显示的余额，与「余额明细」里的数字 必须一致（同一时刻不该出现两个数）
U12 我的佣金 有佣金记录；U8 取消的那单不应变成可提现的佣金
U13 申请提现 提交成功，状态为待审批（下一步到后台第四节的 A15 去审它）
U14 观察项：取消之后再下一单 能不能下？两种结果都可能是对的 —— 照实记下，交给工程判
U15 随手翻一遍各页（我的 / 客服 / 设置） 没有白屏、没有「加载中」卡死、没有看不懂的报错弹窗

四运营后台（电脑，admin 账号）

步骤 做什么 应该看到 不符时记什么
A1 登录 admin / admin123 进入后台，左侧菜单完整，右上角有当前账号
A2 看板 核心指标有数（不是 0、也不是空白）；注意 GMV 含在途退款、成本取净额
A3 看板 与 财务概览 对一遍数 两处的收入/成本/毛利 必须是同一组数字（同一次计算的两次展示）
A4 菜品矩阵 能看到明日套餐与档位；套餐构成确为一饭四菜
A5 订单 → 列表 能看到测试人下的那一单；金额、状态与端上一致
A6 订单 → 详情 金额与端上完全一致（金额一律以「分」为单位显示，不应出现 100 倍误差）
A7 订单 → 配送：改份数 / 司机 / 车牌 能改，保存后刷新仍在；界面对「份数与订单数不符」有提示
A8 开两个浏览器窗口，同时改同一张配送单 必须有一方被提示「已被他人修改，请刷新」 —— 都显示「成功」才是问题
A9 团长 → 列表 / 详情 能看到等级与佣金费率（这是当时的快照，不随后续改等级而变）
A10 团长 → 申请审批 待审批列表可打开；审批后状态随之变化
A11 加工场所 → 打包任务 能打开列表、看到到货明细（这个页只在后台，供应商端没有）
A12 财务 → 概览 有数，且与 A3 的看板一致；余额/冻结这类当下存量不随日期筛选变化
A13 财务 → 佣金 能看到刚那单对应的佣金记录，状态为待入账（还没进余额）
A14 财务 → 余额 余额/冻结有数；可操作动作里包含解冻一项
A15 财务 → 提现审批：审 U13 那笔 能看到待审记录；通过/驳回/已打款/失败四个动作都在，点完状态随之变化
A16 财务 → 对账 页面明确标注「尚未与微信账务对平」 —— 这是如实标注，不是缺陷
A17 财务 → 发票 按 供应商 × 月份 展示，且区分「未开 / 部分 / 已开」三种状态
A18 统计 楼栋排行 / 菜品热度 / 留存都有内容；留存那几个数字要么成对出现、要么同时为空
A19 系统 → 配置：把截单时刻改一个值 → 再看「时刻表」→ 改回原值 时刻表里该任务的执行时刻应当跟着变（这验证「改了配置真的生效」，不是只存不进）
A20 系统 → 操作日志 能看到刚才 A7/A15/A19 这些改动都被记下来了（谁、什么时候、改了什么）

五故意做错的三件事（最能试出问题）

编号 故意怎么做 必须出现的结果 谁做
N1 一天之内，同一个身份下两次单 第二次必须被拦，并说清「哪个出餐日已经下过」；放过去才是 bug 用户端测试人
N2 两个窗口同时改同一张配送单 后提交的那次必须提示冲突并要求刷新；静默覆盖掉别人的填写才是 bug 后台测试人
N3 提现时填一个大于可用余额的金额 应被拒绝并说明原因（余额不足 / 冻结额不足），不应「提交成功」后没有下文 用户端测试人

另外两条更有杀伤力的越权用例（换低权限账号去访问资金接口、服务端数据收窄）由工程用接口直接验， 不在本清单内 —— 让业务测试人手工点，反而测不准。

七收工与复原

什么时候 怎么做
测完关环境 在工程的终端窗口按 Ctrl+C（本次起的服务会一并停掉，不留后台进程）
下次想要一套干净数据 重起时加 --seed：node scripts/local-test.mjs --seed（约 10 秒）
页面打不开 / 白屏 先让工程看 http://<本机IP>:3000/api/v1/health。先排除环境问题，再记为缺陷
手机连不上 九成是 Windows 防火墙拦了 node.exe —— 控制面板 → Windows Defender 防火墙 → 允许应用通过防火墙 → 勾上 node.exe
把结果交回 把第六节那张表（含截图）发给工程。「没发现问题」也要交 —— 那说明这一轮是绿灯，同样是有用的结论

八三条须知（记住就不会误报）

  • 支付是「自动成功」的模拟通道。 看到「已支付」不等于钱到了 —— 别拿它当财务依据，也别惊讶它为什么不用输密码。
  • 系统内部的时间被拨快过。 为了让「任何时间都能下单」，环境把北京小时平移到了 20:00。所以不要拿这个环境验真实时间行为（要按真实时间跑，让工程加 --clock=off 重起）。
  • 数据随手改没关系，但别当权威。 这个环境里的数据是试验场；权威永远是种子脚本与正式库。测完想还原，加 --seed 重起即可。
