## 一、结论先行

**能办到，而且不用自己写聊天功能。** 微信官方给小程序留了两条客服通道，用户点了按钮就直接进微信的
客服会话（跟平时聊天一样的体验），同事在手机另一端接。**同事不需要暴露个人微信号，用户也不需要加好友。**

**我的推荐：直接办 B。** 若你只想先有个入口顶着，也可以先上 A 再换 B ——
但要先接受一个前提：**A 方案的同事收不到可靠提醒**（见 §4.1，社区里长期有「收不到服务通知、
必须点进去才看到」的反馈），所以它只能当过渡，不能当主力。

| 阶段 | 做什么 | 什么时候能用 |
|---|---|---|
| 第一步 | **A · 小程序原生客服消息** | 运营在小程序后台加个客服人员，**当天可用** |
| 第二步 | **B · 微信客服（企业微信）** | 企业微信开通 + 主体验证，约 1–3 个工作日 |
| 切换 | 后台配置里改一个下拉框即可，前端不返工 | 随时 |

理由是：A 零前置依赖、今天就能替掉「复制微信号」；B 是终态（同事在企业微信里接，有接待规则、
转接、统计，手机上随手回）；两者**前端是同一个按钮**，只是唤起方式不同，先做 A 不会白做。

## 二、现状：为什么要改

现在全站 5 个入口（`mine` / `agreement` / `leader-profile` / `order-detail` / `building-switch`）
都跳到同一张 `pages/support/contact.vue`，而这张页的**唯一动作是「复制微信号」**，用户还要
打开微信 → 点「+」→ 添加朋友 → 粘贴 → 等通过，**才能说上第一句话**。

转化损失就发生在这 5 步里。更麻烦的是：加好友之后，这条对话**不在任何系统里**，
掉单、扯皮、换人接手都没有记录。

⚠️ 顺带说明一个口径：**「复制微信号」本身不违规**（售后场景、用户主动点击、非诱导下载 APP，
不命中 5.20 / 5.15.4）。所以要改的不是合规问题，是**体验与留痕问题**。

## 三、先说两条硬约束（它们决定了选型）

### 约束 1：本项目目前**没有 HTTPS / 域名 / 备案**

这一条排除了**自建类**方案：

| 方案 | 结论 | 原因 |
|---|---|---|
| 自建客服后台（会话存档 / 自动回复 / 工单） | ❌ 做不了 | 微信要把用户消息 POST 到**你的**服务器，我们没有公网 HTTPS |
| web-view 嵌 H5 客服页 | ❌ 做不了 | 需要**业务域名**备案 + 根目录放校验文件 |
| 小程序内自建 IM | ❌ 做不了 | 除服务器外还要《即时通信》类目 + 内容安全审核 |
| 第三方 SaaS 客服（芝麻 / 智齿等） | ⚠️ **其实能做** | 回调 URL 由**第三方**提供，我们授权即可，**不需要我们自己的服务器**。代价见 §4.3 |

**换句话说：凡是「消息要进我们自己服务器」的方案，现在都做不了。**
剩下的路有**三条**：A 和 B（消息完全走微信、我们只放入口），以及 C（授权给第三方，见 §4.3）。

### 约束 2：48 小时 / 5 条（A 和 B **都受此限制**，不是某个方案的缺点）

微信对客服通道的统一规则：

| 用户动作 | 客服可回复 | 时限 |
|---|---|---|
| 用户发 1 条消息 | **最多 5 条** | 48 小时 |
| 用户进入客服会话 | 2 条 | 1 分钟 |

条数**不累加**，用户每发一条就刷新一次额度。

**实操影响**：客服不能自顾自连发 6 条。需要在话术里让用户回一句（比如「麻烦回个收到，
我这边接着给你处理」）—— 用户一回复，额度就重置了。这一条要写进给同事的《客服手册》，
不是代码能解决的。

## 四、两条路怎么选（详细对比）

| 维度 | **A · 小程序原生客服消息** | **B · 微信客服（企业微信）** |
|---|---|---|
| 前端写法 | `<button open-type="contact">`（uni-app 原生支持） | `wx.openCustomerServiceChat()`（uni-app 未封装，需 `#ifdef MP-WEIXIN` 条件编译） |
| 前置条件 | 小程序后台「功能 › 客服」添加客服人员（绑同事微信号，≤100 人） | 企业微信开通微信客服 → **企业验证** → 小程序后台绑定**同主体**企业 ID |
| 谁去办 | 小程序管理员，5 分钟 | 需要法人/对公验证，1–3 个工作日 |
| 费用 | **0** | 开通微信客服只需完成**企业验证**（法人验证 / 对公打款验证）；付费「企业认证」是另一件事、可选。以你登录企微后台看到的实际提示为准 |
| 同事在哪接 | 「客服小助手」小程序 或 mpkf 网页端 | **企业微信 App**（手机随手回）/ 微信客服后台 |
| ⭐ **同事能否及时收到提醒** | ❌ **弱且不可靠**（详见 §4.1） | ✅ 企业微信客户端正常推送，跟同事平时收消息一样 |
| 多客服分配 · 转接 | ❌ 无，谁看到谁回 | ✅ 轮流/空闲分配、接待上限、接待时间、超时结束、智能回复 |
| 统计与留痕 | ❌ 基本没有 | ✅ 有基础统计 + 满意度评价 |
| 客服认出用户是谁 | `session-from` 透传一段文本（如「用户1001 · 订单AB…」） | 可自动发一张**小程序卡片**，客服点开直达该订单页 |
| 未验证时的限制 | 无 | 未验证且未绑视频号，**累计仅接待 100 位客户**；验证后解除 |
| 用户端体感 | 点按钮 → 进客服会话 | 点按钮 → 进客服会话，**有新消息提醒**，粘性更好 |
| 开发量 | 极小（1 个按钮 + 1 个配置） | 小（条件编译 + 3 个配置项） |

**一句话区分**：A 是「能用」，B 是「好用」。
A 的短板在客服侧（提醒不可靠、功能简陋、没法分配、没统计）；B 的短板在开通侧（要办企业验证）。

### 4.1 ⭐⭐ A 最要命的短板：同事**收不到可靠提醒**

> 你问的「同事是不是得时刻留意客服小助手」—— **是的，而且比这更糟：提醒不一定来。**

A 的提醒机制是「**服务通知**」：同事第一次打开客服小助手时会被问是否允许发送服务通知，
允许后，用户来咨询时微信平台发一条服务通知。但微信开放社区里有一批长期的反馈说明它**不靠谱**：

| 现象 | 来源 |
|---|---|
| 服务通知**完全收不到**，只能点进客服小助手才看到消息 | 开放社区置顶反馈帖，多人回帖「我也是」「一点也接收不到」 |
| 客服小助手**不弹提示，必须点进去才能看到** | 同上 |
| 网页端不显示消息，**手动刷新才出来** | 社区反馈 |
| 客服需**手动点「在线」**才被分配 | 官方要求（客服小助手右上角设置） |
| 一个客服账号**绑了多个小程序时，只能收到一个**的推送 | 社区反馈 |

**所以 A 的真实成本不是开发成本，是人力盯梢成本**，而且盯了还可能漏。
如果你要的是「同事能及时回」，A **不能当主力**，只能当过渡。

**真要先用 A，至少做这 4 件事**（都是运营侧，不是代码）：
1. 同事首次打开客服小助手时**必须点「允许」服务通知**（拒绝 = 完全收不到）
2. 每次上班**手动点「在线」**
3. 微信里别给客服小助手开**免打扰**
4. 客服小助手账号**只绑我们这一个小程序**，别和其他小程序共用

并且在客服页**如实写服务时间 + 兜底电话**，管理用户预期（A 阶段尤其重要）。

### 4.2 B 为什么就没有这个问题

微信客服的消息直接进**企业微信** —— 同事平时就在用企业微信办公，消息来了**正常弹窗推送**
（跟收同事消息一样，可在企微「设置 › 新消息提醒」里调声音/震动）。
唯一要做的：在企微工作台「微信客服」里开启**「在企业微信里使用微信客服」**并打开消息提醒。

### 4.3 C · 第三方客服 SaaS（B 办不下来时的备选）

之前我把这类方案写成「因为没有 HTTPS 所以做不了」—— **这个判断是错的**，这里更正：
**回调 URL 由第三方提供，我们只是把小程序授权给它们，不需要我们自己的服务器。**

| 维度 | C · 第三方 SaaS（芝麻 / 智齿 / 美洽等） |
|---|---|
| 提醒 | ✅ **可靠** —— 通过服务号模板消息或企业微信推送到同事手机 |
| 服务器 | ✅ 不需要我们的 |
| 功能 | ✅ 机器人、工单、会话存档、统计，比 A/B 都全 |
| 代价 | ⚠️ **付费**（多按坐席/年收费）· ⚠️ 要把小程序 AppID/AppSecret **授权给第三方**（数据出域，隐私政策需同步说明）· ⚠️ 多一个供应商要管 |
| 接线 | 小程序后台开启消息推送（填第三方给的 URL）+ **关闭「在官方客服工作台收发消息」** |

**不推荐做首选**，但它是「B 办不下来」时的保底。

## 五、推荐做法：一个按钮，两种模式，配置切换

沿用项目既有纪律 —— **联系方式一律服务端下发，端上不硬编码**（换号、换客服账号只改后台配置，
不用重新发版）。所以做法是：

### 5.1 后台新增 3 个配置项（`ab_config`，走现有声明式配置体系）

| key | 类型 | 说明 | 缺省 |
|---|---|---|---|
| `service.cs_mode` | select | `none` 复制微信号（现状）/ `contact` 原生客服 / `wechat_kf` 微信客服 | `none` |
| `service.cs_corpid` | text | 微信客服的企业 ID（仅 B 模式用） | 空 |
| `service.cs_url` | text | 微信客服的客服链接（仅 B 模式用） | 空 |

`config.specs.ts` 里声明好，后台配置页会自动出现，运营自己就能切。
⚠️ `cs_corpid` / `cs_url` 配了但 `cs_mode` 不是 `wechat_kf` 时，端上**必须忽略**它们 ——
避免出现「配了一半、按钮点了没反应」的情况。

### 5.2 客服页改造（`pages/support/contact.vue`）

现在页面顶部是「微信号 + 复制按钮」，改成：

```
┌─────────────────────────────┐
│  在线客服                     │   ← 主按钮（按 cs_mode 决定点下去发生什么）
│  工作日 9:00–18:00 即时回复    │
│  [ 发起在线咨询 ]             │
├─────────────────────────────┤
│  非工作时间 / 紧急情况        │   ← 原来那块降为兜底，折叠起来
│  微信号：abox_service  [复制]  │
│  客服电话：xxx  [拨打]         │
└─────────────────────────────┘
```

`cs_mode=none` 时（现在的状态、以及将来微信客服挂了的降级态），主按钮自动退回「复制微信号」，
页面和现在长得一样 —— 保证了**任何时候都不会出现点了没反应的按钮**。

### 5.3 让同事一眼认出「这是谁、哪一单」

这是两条路**都存在的真实短板**：用户进了客服会话，客服看到的只是一个微信昵称。
不加处理的后果是同事第一句必然问「请问你是哪位、订单号多少」—— 又回到低效率。

| 模式 | 做法 |
|---|---|
| A | 按钮上带 `session-from`，把 `userId + 当前订单号` 透传过去，客服在客服小助手里能看到来源信息 |
| B | `showMessageCard + sendMessagePath`，用户进会话时**自动发一张小程序卡片**，客服点开直达该订单详情页 |

⚠️ **修正一处方案里的错误**：原写「`userId` + 手机号尾号」—— 本项目 **C3 不取手机号**
（`ab_user.phone` 恒为 `null`），**没有手机号尾号可透传**。所以客服侧能识别的只有
`userId`（+微信昵称）。B 档靠**订单卡片**弥补这个短板，也因此**更该直接上 B**。

⚠️ B 有个已知坑：`sendMessagePath` 的小程序路径**必须加 `.html` 后缀**
（如 `/pages/order-detail/order-detail.html?orderNo=xxx`），不加会提示「页面不存在」。

### 5.4 其他入口（可选，看你要不要一次做完）

`order-detail` 的「联系客服」可以升级为**「咨询这一单」** —— 直接把当前订单号带进会话。
对售后场景（代退、退款进度）价值最大。其余 4 处维持现状即可。

### 非开发侧（这个更重要，得有人去点）

**A 模式**：
1. 小程序管理员进 mp 后台 → 「功能 › 客服」→ 添加客服人员 → 填同事的微信号
2. 同事在微信里搜「**客服小助手**」小程序，就能收到并回复用户消息

**B 模式**：
1. 注册/登录企业微信 → 应用管理 → 开通**微信客服** → 完成企业验证
2. 创建客服账号，设置接待人员（同事）、接待规则、接待时间
3. 「在微信内其他场景接入」→ 复制**客服链接**
4. 「我的企业」底部复制**企业 ID**
5. 小程序后台 → 「功能 › 客服 › 微信客服」→ 填企业 ID 绑定

⚠️ **企业 ID 必须与小程序主体一致**（北京巡礼之年科技有限公司），否则绑定不了。

## 七、坑与纪律（写下来免得后面踩）

| # | 坑 | 应对 |
|---|---|---|
| 1 | 客服 48h 内只能连回 5 条 | 写进《客服手册》：让用户回一句就能重置额度 |
| 2 | `sendMessagePath` 不加 `.html` → 卡片点开「页面不存在」 | 路径统一带后缀 |
| 3 | uni-app 没封装 `openCustomerServiceChat` | **平台探测**（运行时取 `wx.openCustomerServiceChat`，取不到即降级）—— ⚠️ **不是**条件编译，见上文「实施偏差①」 |
| 4 | **开发者工具里客服会话不生效** | 必须**真机 + 体验版**验证（跟之前同事测小程序的口径一致） |
| 5 | 客服小助手与微信客服是**两套工作台** | 同一时期只启用一种，别让同事盯两个地方 |
| 6 | 配了 corpId 但 mode 没切 | 端上以 mode 为准，避免「点了没反应」 |
| 7 | ⚠️ 规范明令禁止**恶意诱导用户触发客服消息**以达到下发消息的目的 | 客服入口只在用户需要时出现，不做弹窗诱导 |

## 八·补 给同事的一页纸（《客服手册》要点）

**① 在哪接**：企业微信 App → 工作台 → **微信客服**（不是微信、不是客服小助手）。
⚠️ 首次要在企微工作台「微信客服」里开启**「在企业微信里使用微信客服」**并打开消息提醒，否则不弹窗。

**② 48 小时 / 5 条（最容易踩）**：用户发 1 条，你**48 小时内最多连回 5 条**，条数不累加。
发满 5 条后就**发不出去了**，而系统不会告诉你为什么。
→ 话术：说完第 4 句就让用户回一句（「麻烦回个收到，我接着给你处理」），**用户一回复额度就重置**。

**③ 认出用户是谁**：用户进会话时会**自动发来一张小程序卡片**（标题含用户编号与订单号），
**点开卡片直达那一单**。别再问「请问你是哪位、订单号多少」—— 直接看卡片。

**④ 认不出的情况**：用户没从订单页进来（从「我的 › 联系客服」进）时没有订单号，
只有用户编号。这时才需要问一句。

**⑤ 兜底**：在线客服挂了 / 非工作时间，用户会看到「其他联系方式」（微信号 + 电话）。
页面永远有一个能用的通道。

## 九、不做的事（避免后面有人再提）

- ❌ 小程序内自建聊天（要《即时通信》类目 + 内容安全 + 长连接服务，远超一期）
- ⚠️ 引第三方 SaaS 客服 —— **技术上可行**（回调 URL 由第三方提供，不需要我们的服务器，
  §4.3 已更正此前判断），但需**付费 + 授权第三方 + 数据出域** ⇒ 只作为「B 办不下来」时的保底
- ❌ web-view 嵌 H5 客服（需要已备案业务域名）
- ❌ 为了「能主动找用户」去诱导用户点客服按钮（违反客服消息使用规范）
