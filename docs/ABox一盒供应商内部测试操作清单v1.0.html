三条最容易被误报成 bug 的事，先记住
  • 登录后第一眼是空的。 系统会把供应商送到「概览」页，而那页尚未实装，显示「脚手架占位页」。 请点左侧 商家工作台 继续 —— 这不是登录失败，也不是权限错。
  • 菜单里的「我的菜品」「上架申请 / 商家资料」同样是空的。 这两页尚未实装， 不影响本轮（本轮只验「出餐 → 结算」这条真实链路）。
  • 结算页看不到售价与佣金，是刻意的。 你和平台是采购关系，按约定你只该看到 「我的协商单价 × 我的交付量」。这一页出现 ¥25.80 或佣金额，才是问题。
✅ 一条关于「确认出餐」的说明（2026-09-18 起已变化，别照旧报告）
  • 「确认出餐」现在还会把订单推进到「已出餐」。除了写你那边的出餐计划与应付单（这是本节 S1–S18 要验的），它同时是「出餐 → 配送 → 佣金」这条链的起点：没有这一步，后面的配送推进与佣金都动不起来。
  • 所以：你确认出餐之后去后台订单页看，订单应当从「已截单」变成「已出餐」。仍然停在「已截单」才是问题（请按 P1 记，注明「出餐确认后订单未推进」）。
  • ⚠️ 注意范围：只有本加工场所、本出餐日的、且当时正停在「已截单」的订单会被推进；已退款/已取消的单不受影响。

S2 点左侧「商家工作台」
（别停在登录后那个空页）		 顶部显示「三味屋 · 合作中」；出餐日自动落在明日（最近一个有计划的出餐日）
S3 看上面 4 个数字块 应出餐份数 45 · 已确认送达 0 · 待确认 45 · 涉及集散中心 1
S4 看「确认截止」提示条 写着「出餐确认截止 09:30」，并说明提前备好即可提前确认
S5 看菜品卡 菜品是你名下供的菜（本轮是红烧肉）；写着「采购单价 ¥7.50 · 应出 45 份」
S6 看卡片里那张小表 一行：集散中心 1（国贸/建外）· 朝阳区建国路 88 号 · 应送 45 · 实送 —（未登记）· 待送达
S7 看页面底部「口径说明」 三条讲清：截止 09:30；份数生成后即冻结；本页份数是生产口径，不做结算依据

S3 里的 45 份来自预置的演示数据（明日一团的已售份数）。若工程先让人在用户端下了单并跑过截单， 这个数会随之下变 —— 照实记录你看到的数即可。单价 ¥7.50 同理，是协商价示例值。

四出餐确认（本轮的核心动作）

步骤 做什么 应该看到 不符时记什么
S8 点左侧「出餐确认」
（或工作台右上角那个按钮）		 列表按「一道菜 × 一个集散中心」逐行展开；未确认的行默认已勾选
S9 第一遍：不改份数，直接提交 提示「出餐确认成功：1 项」，并补一句「本日出餐任务已全部确认完成，集散中心可以开始打包」
S10 第二遍：原样再提交一次 提示「已提交：新增确认 0 项，跳过 1 项（此前已确认）」—— 不报错才是对的
S11 回「商家工作台」刷新 已确认送达 45 · 待确认 0；菜品状态变「已全部送达」；小表那行变「已送达」并带确认时间
S12 短送演练（想做就做，但要在 S9 之前） 把某行「实送份数」改小（如 30）→ 提交时先弹「份数差异提示」→ 确认后照常成功
两条判据（反直觉，但拦住了才是对的）
  • 重复提交不该报错。 网络重试是常态，系统把已确认过的项原样跳过并告诉你 —— 报「重复提交错误」反而是缺陷。
  • 份数不一致不等于填错了。 短送就该如实申报：短送即少付（计费基数是你的实收量）， 所以如实填既是对账依据，也是你自己的收款依据。系统会先确认一次，不会静默放过。

五应付结算明细（看点：钱怎么算）

这一节需要工程先跑一次应付跑批（见第七节）。没跑之前，这页本来就该是空的 —— 先照 S13 确认「空得有理」，再让工程跑批。

步骤 做什么 应该看到 不符时记什么
S13 点左侧「应付结算明细」 日期默认今天，表格为空并给出说明 —— 这是正常的（应付单在出餐日之后才生成）
S14 把日期改成 出餐日（第三节看到的那个日期） 出现 1 行应付：应付单号 SH… · 菜品 · 实收 45 · 我的单价 ¥7.50 · 应付 ¥337.50 · 待付款
S15 看 4 个汇总块 平台待付合计 ¥337.50（全部日期 · 1 单）；其中已付款 ¥0.00；当日实收份数 45
S16 自己把数算一遍 实收份数 × 我的单价 必须等于应付金额（45 × 7.50 = 337.50）。若 S12 做过短送，应随之变少
S17 翻一遍整页找两样东西 找不到 ¥25.80、也找不到「佣金」「毛利」→ 找不到才对（找到了是问题）
S18 看页面上的口径说明 讲清两件事：付款走人工对公转账（回单号是付款完成的唯一凭证）；有异议以出餐确认当时的留痕为准

六故意做错的四件事（最能试出问题）

编号 故意怎么做 必须出现的结果 谁做
N1 在地址栏手输一个运营页地址，如 /finance/overview 打不开 / 被挡在权限页；绝不能看到运营的财务数据（看到了就是最严重的问题） 供应商测试人
N2 出餐确认时，把实送份数填 0 或负数 应被拒绝并说明原因；不应「提交成功」后没有下文 供应商测试人
N3 在提交内容里塞一个别人的供应商编号（如 supplierId=2） 应被直接拒绝 —— 不接受「替别的供应商确认」。这条由工程用接口验 工程
N4 过了截止时间再做出餐确认（让工程把环境时间调过 09:30） 应被拒并提示已过截止、不再受理补确认；系统不该「通融」 工程 + 供应商

还有两条更底层的越权用例（换低权限账号访问资金接口、服务端是否按账号收窄数据范围）由工程用接口直接验， 不在本清单内 —— 让业务测试人手工点，反而测不准。

七工程准备：让「结算」有数（一次性）

做什么 命令 / 操作 做完应该看到
让供应商能看到出餐计划 起环境时已含演示数据；无需额外操作，工作台直接有 45 份的计划 工作台有菜品与集散中心
让供应商的结算页有数 用 admin 登录后台，调一次应付跑批： POST /admin/schedule/supplier-share/run，请求体 {"date":"<出餐日>"} 返回里有 created 一行； 未做出餐确认的供应商会出现在 exceptions 里（原因写着「出餐确认尚未开始」）
想连截单链路一起验 先让人在用户端下一单，再补跑 POST /admin/schedule/cutoff/run（同样带 date） 工作台的「应出餐份数」随实际售出份数变化
为什么结算页「先空后有」不是 bug
  • 应付单按设计在出餐日之后的凌晨按实收量生成，所以查「今天」常常是空的 —— 页面自己会给这句说明。
  • 没做出餐确认，就不会出应付单。 这是刻意的：确认是「交付依据」，没有它平台既无凭证也无实收量。 本轮三味屋出了单、另外三家出现在 exceptions 里，正是这条规则的现场证明。

十四条须知（记住就不会误报）

  • 供应商没有独立系统。 你和运营进的是同一个后台网址，只是登录后各自看到的菜单不同 —— 这是设计，不是「走错门」。
  • 三页是空的，且是已知的。 「概览」（登录默认页）、「我的菜品」、「上架申请 / 商家资料」尚未实装，会显示「脚手架占位页」。它们不影响本轮。
  • 看不到终端售价与佣金，是刻意的。 平台与你之间是采购关系：你只看到「我的协商单价 × 我的交付量」。这页出现 ¥25.80 或佣金额，才是缺陷。
  • 这里的钱不真转。 跑批生成的应付单不会真的打款，付款在正式流程里走人工对公转账并回填银行回单号。别拿这份单子当收款依据。
