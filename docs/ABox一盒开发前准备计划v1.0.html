四、阶段一 · 口径与文档就位

第 1 周 · D1–D3 · 约 3 个工作日
目标：让全套设计文档与原型口径 100% 一致，形成开发阶段唯一的「事实来源」（Single Source of Truth），杜绝「文档说 A、原型做 B」的返工。
  1. 文档版本归一：PRD / ER 文件由 v2.0.md 改名为 v2.1.md，并修正文档信息表中的版本号与变更记录。
  2. 目录结构升级 v1.0 → v2.0：删除「楼长端」目录（L2 已定无楼长）、截单时间 T-1 20:00 改为 T-1 24:00、口径统一为「4 角色 · 3 载体」、增补 P38「今日这盒」与集散中心配置相关结构。
  3. 产出《设计 token 规范 v1.0》：把《执行报告》中散落的 token 表独立成文
    • 色彩（米色 / 暖棕 / 金棕 + 三状态色）、字阶、间距、圆角、阴影
    • 与 Element Plus 后台的变量映射表（一套 token 两端复用）
    • 楷体在真机上的降级方案（wx.loadFontFace → 系统楷体族 → serif）
  4. 回填 P38 字段清单至 PRD，正式收口 C8 定位（只展示本餐 4–5 家 + 资质 / 评分 / 今日菜品）。
  5. 冻结「v1.0 基线」：全套文档 + 原型打快照（记录目录 hash 或 git tag），此后任何变更一律走变更流程。
关键交付物：PRD v2.1（归档）· ER v2.1（归档）· 项目目录结构 v2.0 · 设计 token 规范 v1.0 · 基线冻结清单
验收标准：以《审查报告 29 项清单》做一次回归比对，文档与原型 0 冲突。

五、阶段二 · 接口与技术设计定稿

第 1 周末 – 第 2 周初 · D3–D6 · 约 3–4 个工作日
目标：让前端有「契约」、后端有「表」—— 这是前后端能并行开工的前提。
  1. 产出《API 接口规范 v1.0》：按 3 载体分域（小程序 / 供应商 Web / 运营后台），统一响应结构、鉴权（小程序 JWT + wx-signature、后台 JWT + RBAC）、分页、错误码、幂等键。
  2. 订单状态机定稿：用户 5 态 ↔ 团长 6 态 ↔ 后台 8 态三端映射表 ＋ 全链路状态流转图；明确「截单瞬间系统做什么」与「手动确认 / 自动确认冲突时先到为准」。
  3. 表结构评审（26 → 27 张）：逐张过一遍；补 ab_leader_invite 表支撑 C2 晋级审计；复核订单按月分区、deleted_at 软删除、version 乐观锁。
  4. 关键技术专项评审（对应交接包 D 方向）
    • 定时任务补偿与重试：T-1 24:00 截单、T 日 14:00 自动确认、T+1 02:00 分账
    • 多集散中心并行配送的数据一致性
    • 「反向分账」：已分账后发生退款如何回退
    • 队列选型结论落地 —— MVP 用 Redis + BullMQ，不引入 RabbitMQ
  5. 数据字典 ＋ 种子数据清单：4 供应商 / 6 备选 / 菜品与成本价 / 4 集散中心（复用合作供应商场地 · 场地/打包费默认 ¥0 · C9 修订）/ 12 栋楼 / 5 楼群 / 14 位团长 / 4 级佣金 / 统一价 ¥25.80。
关键交付物：API 接口规范 v1.0 · 订单状态机与全链路流转图 v1.0 · 表结构评审意见 v1.0 · 种子数据清单 v1.0
验收标准：接口覆盖 PRD §3.1–3.4 全部 M 编号功能；每一张表都能追溯到具体接口。

六、阶段三 · 账号、合规与外部对接（并行）

第 1 周启动 · 核对 1–2 天 · 与阶段一 / 二并行
目标：把「卡上线」的外部依赖全部打通。三项长周期资源已就绪，本阶段重点是核对、归档与联调准备。
  1. 小程序侧：AppID / AppSecret 归档；类目确认（餐饮 → 热食类制售，需《食品经营许可证》）；服务器域名白名单登记（request / uploadFile / downloadFile / socket）；订阅消息模板申请（下单成功 / 出餐 / 取餐 / 退款结果）。
  2. 微信支付侧：商户号与小程序关联；JSAPI 支付开通；退款 API；灵活用工平台开户（团长佣金代发 + 个税代扣 · C11；供应商 / 集散中心走人工对公转账·日结，不需要分账、也不再需要「商家转账到零钱」）；APIv3 密钥与证书归档（apiclient_key.pem / 平台证书）。
  3. 云资源开通：服务器（先 Docker 单机，预留 K8s）、MySQL 8 实例、Redis 7、COS 存储桶 + CDN、域名解析与 HTTPS 证书。
  4. 资质与法务：《食品经营许可证》；《团长合作协议》简版（1 页内，注册页勾选用）；隐私政策 ＋ 用户协议。
  5. 密钥与账号交接清单：所有密钥统一归档到保管位置，形成《账号资源与密钥清单》，避免散落在个人聊天记录里。
关键交付物：账号资源与密钥清单 · 域名白名单登记表 · 支付产品开通确认 · 资质文件包 · 协议文本（团长 / 隐私 / 用户）
验收标准：能跑通「小程序登录 → 支付下单 → 支付回调 → 分账 / 提现」的最小链路验证（沙箱或正式环境）。

七、阶段四 · 工程基建与协作机制

第 2 周 · D6–D10 · 约 4–5 个工作日
目标：让开发专家团「代码拉下来就能跑」—— 一条命令起环境，一份规范无争议。
  1. Monorepo 脚手架：pnpm workspaces 初始化；apps/miniprogram（uni-app Vue3 + Vite + TS）、apps/admin-web（Vue3 + Element Plus）、apps/api-server（NestJS）、packages/（shared-types / shared-utils / eslint-config / tsconfig）。
  2. 本地环境：docker-compose.yml（MySQL 8 / Redis 7）、.env.example、scripts/setup.sh 一键初始化、数据库迁移与种子脚本。
  3. 工程规范：ESLint / Prettier / commitlint / husky；分支策略 main / develop / feature/*；提交规范（Conventional Commits）；Code Review 流程。
  4. CI/CD：Actions 流水线（lint + test + build）；测试框架落地（Jest 单测 ＋ supertest e2e ＋ uni-automator）。
  5. 协作机制：双周迭代节奏；需求变更流程（一律先回写文档 + 记变更）；验收 SOP；问题跟踪看板；文档库结构（docs/）。
  6. 开发里程碑计划：把 5–6 周开发切分为 M1–M5（见文末附录）。
关键交付物：可运行仓库 abox-onebox · setup.sh 一键起环境 · CI 配置 · 协作规范 v1.0 · 开发里程碑计划
验收标准：新人在 30 分钟内跑起本地全栈；CI 首次全绿。

十、启动评审与交接（引入开发专家团）

准备期的终点不是「文档写完」，而是一次正式的评审与冻结。建议在第 2 周末（D10）安排一次约 1 小时的启动评审：

  1. 逐项核对四阶段的 15 项交付物，确认无遗漏、无「待办占位」。
  2. 冻结基线：打上 v1.0-baseline tag，作为开发阶段唯一的输入版本。
  3. 签署纪要：产出《开发启动评审纪要》，明确开发范围、里程碑、验收标准与变更流程。
  4. 引入开发专家团：以基线文档为唯一输入启动编码，按 M1–M5 推进。
✅ 完成以上四步，「准备期」正式收官，「开发期」正式开启。此时专家团拿到的是：冻结的 PRD ＋ 定稿的接口规范 ＋ 定型的表结构 ＋ 可运行仓库 ＋ 就绪的账号资源 —— 无需再回头补设计，也不存在口径争议。
