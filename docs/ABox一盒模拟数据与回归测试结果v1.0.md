## 二、补了什么数据：两层种子纪律

⚠️ **刻意分成两层，不合并** —— 这不是洁癖，是避免「与被测产物无关的假红」。

| 层 | 命令 | 内容 | 谁用 |
| --- | --- | --- | --- |
| 基础主数据 | `gate.mjs seed` | 12 楼 / 5 团长 / 4 供应商 / 菜品 / 套餐 / 配置 —— **零订单** | **e2e 的前置**（`gate.mjs all verify` 尾部会跑它） |
| 演示 / 边界数据集 | `gate.mjs seed:demo` | 在基础层之上**叠加** 34 单演示数据 | **人工测试的人**（`local-test.mjs --seed` 默认叠加） |

**为什么必须分开**：`e2e:m3` 有多处**绝对值**断言（D1 排期格数 / 三味屋当日加工场所数 / 发票分母 / 干净候选池）依赖「库里只有基础主数据」。把演示数据并进 `seed` 会让这些断言**全部变红**，而那**不是产品缺陷**，纯属测试自身被干扰。

### 2.2 刻意造的边界与异常样本（11 类）

1. 未支付订单**不自动取消**（停 `pending_pay`）
2. 截单跑批**漏跑** → 订单停在 `paid`（测「补跑接口能把这天补回来」）
3. 单次下单**上限 20 份**的边界量
4. `refunding` **保留态**探针（订单永不进入，但状态机保留）
5. 退款**已到账**的佣金**反向冲销**（`cancelled` 原行 + `reversal` 负行）
6. 退款**在途**时**不提前**冲销（`refund_applying` 期间佣金仍在）
7. 配送单**一步未推**（`cooked` 已确认、配送单仍 `pending` → 可当场练 A7b/A7c）
8. 配送**份数与订单不符**（人工修正入口 D62 的靶子）
9. **停职团长的历史费率快照**（同楼两档费率并存）
10. **今日完成 → 佣金 `pending`**（两段式第一段）
11. **已送达但团长未确认收货 → 尚无佣金行**

### 2.3 数据隔离设计（关键）

演示数据只用 **楼群 4 / 5**、楼栋 **8 / 9 / 11 / 12**、专用 `openid LIKE 'demo_abox_%'` 与单号前缀（**`AB0000`** / `WDDEMO` / `RFDEMO` / `DMDEMO`）—— 与 e2e 密集使用的 **1 / 2 / 3 楼群完全错开**，故两套数据**互不干扰**、可同时存在。

> ⚠️ **订单前缀是 `AB0000`（2026-09-18 M5-11 · 缺陷 #93）**：原用 `ABDEMO`，而演示订单号必须能过
> **自家读取侧校验** `^AB\d{16}$` —— `ABDEMO2026091830` 含字母、长度 14 → **端上点开任何一单演示订单
> 都直接 `10001 orderNo 格式不合法`**（列表刷得出来、详情页打不开）。新前缀取「年份位 `0000`」：
> 真实单号的年份来自 `todayBj()`，**「0000 年」永不可能被生成** ⇒ 既是清理键、又不撞真实单号。
> 提现 / 退款 / 余额调整三类单号**不受该正则约束**，故保留 `…DEMO`。

## 四、失败项与可能原因

### 4.1 真缺陷（已修复）—— 2 项

| # | 现象 | 为什么一直没被发现 | 修法 |
| --- | --- | --- | --- |
| **#87** | 发票「**部分开票**」这一态**永远造不出来**：数据里明明存在「同一供应商同一月、部分行已开票」的形状，但页面永远只显示「已开 / 未开」两种 | 自检只校验了**行级字段**、没校验**视图级聚合判定**；而未付款行**不进开票分母** → 供应商 2 被误判成「全开」，`partialCount` 恒为 0 —— **不报任何错，界面只是少一块内容** | 发票三态按 supplier 显式分派；供应商 2 走 `partial` 且**只对已付款行**开一部分 |
| **#88** | 演示数据只造了「**过去**」，于是 **4 处页面的默认视图打开就是空的**（库里数据一张不少） | 4 处页面默认日期 = **今天**（佣金明细 / 打包任务 / 看板「今日」档 / 配送单取**最近**配送日）；数据全在 T-2 及更早 | 补 **T 日** 订单 seq 30–34 + T 日配送单；佣金改**日期感知**（`dayOffset <= -1` 才 `settled`，今天 → `pending`） |

⭐ **这两条的共性价值**：**自检 12 项全绿（当时口径），探针首跑才盘出来**。自检验证的是「**写进库是对的**」（写侧），探针验证的是「**接口按页面默认视图给得出**」（读侧）—— 这是两件事，**不能互相替代**。

> ⚠️ **同一族缺陷后来又有一次（#93 · 2026-09-18 M5-11）**：演示单号前缀 `ABDEMO` 不满足**自家**
> `^AB\d{16}$` → 端上点开任何演示订单都 `10001`。它同样是**自检全绿时活下来的**：
> 自检只问「这批数据自己自洽吗」，**不问「它进得了门吗」**。
> 故补齐第 ⑬ 项自检（调**生产校验函数** `isOrderNo()` 逐张验形）+ 探针新增「读取侧校验」小节
> （**正证 + 反证成对**）—— **判据升级为：种子数据必须走一遍自家的读取侧参数校验。**

### 4.2 探针自身的错误 —— 6 项（非产品缺陷）

首跑 8 项红中，6 项是**探针写错了对出参形状的假设**（没读实现就猜）：

| 探针的错 | 实际 |
| --- | --- |
| 以为 `building-rank` 返回 `list` | 实为 `groups` / `buildings` |
| 以为余额冻结字段叫 `frozen` | 实为 **`frozenFen`** |
| 以为对账 `list` 非空才算通过 | `list` **只装差异行**，「空」才是**正确**语义 |
| 以为打包任务返回 `list` | 实为 `centers` |
| 发票月份阈值写得过严 | 应为「不小于本月」 |
| 佣金状态断言**用错了日期** | 应按「结算账期」而非「出餐日」取数 |

**教训**：写断言前**先读端点实现**。猜形状产生的红，排查成本高于漏断言。

### 4.3 一轮「被环境干扰」的假红（已通过设计消除）

`gate.mjs all verify` 尾部的 `seed` 会**抹掉**演示数据，且 e2e 套件会在**别的楼群 / 日期**留单（其中一单是「**明日**」→ 配送单默认日期被推到 `2026-09-19`），导致探针出现 2 项红。
**对策**：探针用「演示单号前缀」把「默认视图有数据」的断言**收敛到演示行**，并在检测到非演示数据时**主动提示**；**干净库与残留库都要跑**。

## 五、预期行为（不是缺陷 · 已在测试清单里写明）

⚠️ 以下三条**看起来像 bug，实际是正确行为**。已在《内部测试操作清单》文首以绿色提示块写明，避免测试人误记成缺陷：

| 现象 | 为什么是预期的 |
| --- | --- |
| **对账页默认空** | 对账锚 = **支付日**（微信账单按支付日切日），而演示数据的支付日都在过去；改查「某个出餐日的前一天」即可看到 |

| **今日佣金显示「待结算」** | 佣金是**两段式**：T 日 14:00 计佣写 `pending`（只记账），**T+1 02:00 才入账**；今天的单**本来**就该是 `pending` |

另有 **1 条如实告警（不粉饰）**：账户 `#2615` 的资金恒等式差额 **¥-2.32**，**恰好等于已结算佣金的冲销额**。原因是**冲销只扣 `balance`、不动 `total_in` / `total_out`** —— 这是当前口径的**已知偏差**，不是算错。若将来要让恒等式严格成立，需另立批次讨论「冲销是否计入累计流出」。

### 3.1 §36 到底在验什么（为什么要新加 10 条断言）

#49 之后，「业务时刻的唯一真相 = `order-timeline.ts` 的 `DEFAULT_TIMELINE`」是靠**结构性派生**兜住的 —— `TASK_SCHEDULES[*].cron` 与下单窗口锚点**都是它的派生值**。

⚠️ 但**派生只保证「同一份源」**，不保证「外部看到的就是它」：把配置写进 `ab_config`、跑一次热重载、`GET /admin/schedule` 读回来，这条链**从来没有人黑盒走通过**。

§36 的写法有一条硬约束：**出厂口径在脚本内写死复刻，刻意不 `import` 服务端常量**。

> 理由：如果断言也 `import DEFAULT_TIMELINE`，那就是「拿实现验实现」—— 实现改错了，断言跟着一起错，**两边互相担保而恒绿**。只有**两条独立路径**（实现一份、脚本一份）才能互相证伪。

十组断言：

| 组 | 验什么 |
| --- | --- |
| A · 起点归一 | 写回出厂值 → 8 个任务**全部注册**且 `registeredCron === cron`（不先归零，后续「偏离」无法判定） |
| B · 正向 ①②③ | 批量写配置 → ① D57 逐键读回一致 ② `effectiveAt` 与 `registeredCron` **双到位** ③ 送达时刻在**时刻表不留行**（它由 `ab_config` 表达而非任务） |
| B · **反向** | 偏离出厂值的任务集 **恰好等于** 被覆写配置键对应的任务集（防「改了 A 却影响 B」与「改了 A 但 A 没变」两种不报错的错） |
| B · 出厂列 | 有配置覆写时，**出厂列不被污染**（否则「被改过」这件事看不出来） |
| B · 派生日期 | 截单 `24:00` → `today` · `23:30` → `tomorrow`（`dateKind` 必须是**算出来的**） |
| C · **反证** | 4 个**不可配**任务在「配置全改」时**仍为出厂值** —— ⭐ 这条是关键：只验正例会漏掉「时刻表其实压根没读配置」这种情况 |
| D · fail-closed | 非法值 `25:00` → `10001`，且**不半生效**（不写入一个坏值、也不留一半改一半） |
| E · 复原 | 节末写回出厂值并**断言复原**（本节真改过配置，不还原会把「被改过的时刻表」留给后续节与重跑） |

### 4.1 「等级 → 费率」为什么算真缺陷（收口前是「2 个来源 × 4 个消费点」）

| 消费点 | 收口前读的是 | 收口后 |
| --- | --- | --- |
| `promotion.service`（自动晋级审计） | **配置** `ab_config.commission.rate.*` | 配置（未变） |
| `team-leader.service`（L17 建档案 / 复职） | **常量** `LEADER_LEVEL_META[level].rate` | **配置** |
| `leader-admin.rateOf()`（D20 任命 / D21 改等级） | **常量** | **配置** |
| `LeaderLevelService.rules()`（L16 出参） | **常量** | **配置** |

判据不是「有人算错了」，而是 —— **`config.specs.ts` 把四条费率键声明为 `wiring: 'live'`、类注释也写「费率最终以 `ab_config` 为准」，而实现里只有 1/4 条路径真读配置**；运营把金牌费率从 10% 改成 11%，**端上等级表、后台下拉、建档与改等级的写库值全部照旧**，而**两侧都不报错**。

收口后：**费率真源 = `ab_config`；常量只作「出厂兜底」**（配置读不到时才有意义）。

### 4.2 §37 的九条断言（判据是**双向**的）

| 组 | 验什么 |
| --- | --- |
| A · 夹具前态 | 4 条费率配置齐备 · 靶子团长（`dev:1003` 张磊 · formal）在职且**不是 gold**（改完能改回去） |

| C1 / C1b | L16 `rules()` 出参 `gold = 0.11`，且 **trainee / formal / chief 纹丝不动**（防「取费率的口退化成一个值」） |

### 4.3 ⚠️ 本批踩到的两件事（都可复用）

1. **断言口径错，不是实现错（§37 C3 首跑红）** —— 实现是对的（`db = 0.11` ≠ 常量 `0.10` ⇒ 确实读了配置）；红在**我写的断言拿「驱动返回形状」当了业务缺陷**：`ab_team_leader.commission_rate` 是 `DECIMAL`，sqlite 读回 **number**（`0.11`），而 `ab_config.config_value` 是 **VARCHAR**（`'0.1100'`）。**判据：跨表断言前先确认该列的读回类型**；同文件既有断言一律用 `Number(v).toFixed(4)`，照抄即可。
2. **取断言总数必须直跑脚本** —— `gate.mjs` **成功时吞掉子进程 stdout**（失败时才打印全套明细），故「m3 到底多少条」在 `gate.mjs e2e:m3` 的成功输出里**看不到**；要**复刻 gate 的 env 直跑**（`E2E_PORT=3103` + `ABOX_SHIFT_TO_HOUR=20` + `QUEUE_DRIVER=memory` + `QUEUE_BACKOFF_BASE_MS=20`），且**必须先 `seed`**（否则会在 §16 崩于 `TypeError: Provided value cannot be bound to SQLite parameter 1` —— 上一轮的库状态已被吃空、某 id 为 `undefined`，**看起来很像是套件坏了**）。
